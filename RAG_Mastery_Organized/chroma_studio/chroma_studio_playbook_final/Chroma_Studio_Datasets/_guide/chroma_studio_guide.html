Chroma Studio — User Guide

A local tool to create, edit, filter, and visualize a Chroma vector database — built for your environment (in-house Jina embeddings, no forced HuggingFace download). This guide walks every feature using the datasets you already have, ending with the API-discovery use case.

01 Getting started

Chroma Studio is a Streamlit app. It reads and writes a local Chroma database folder (the one containing chroma.sqlite3), and only one process may use that folder at a time.

Install & run

# from inside your chroma_lab_env (the venv with chromadb 1.5.9)
pip install -r requirements.txt
streamlit run app.py

One process at a time

Because it uses a local PersistentClient, close anything else that holds the same folder open — another notebook, or ChromaFlowStudio — before running Studio. A lock error almost always means a second process is already attached.

02 Connect & pick an embedding source

Everything is set in the left sidebar.

  1. Local Chroma folder — the path to your database folder, e.g. D:\practice_chroma or the path an ingestion notebook printed.
  2. Embedding source — In-house Jina (hosted) is the default for your environment: enter the base URL + API key. Or Local model to point at a downloaded sentence-transformers model folder.

Good to know: embeddings are only computed when you add or update a document, or run a text search. Browsing, filtering, and deleting never call the embedder — so even if the model is misconfigured, you can still manage existing data.

03 The five tabs

Browse
Page through documents and their metadata. Includes the metadata summary panel, the structured metadata filter, and a free-text filter.
Add
Add documents one at a time (with an optional metadata JSON) or in bulk (one document per line). Embeddings are computed on add.
Edit / Update
Change a document's text (re-embeds) or just its metadata (instant, no re-embed). Delete a single document.
Visualize
Project the embedding space to 2D or 3D with PCA, t-SNE, or UMAP; color by metadata or KMeans cluster; filter the plot by metadata; drill into clusters.
Manage
Create a collection (choose cosine / l2 / ip distance) or delete one.

04 Metadata & filtering

Metadata is what turns a pile of vectors into something you can slice, audit, and scope. Studio surfaces it in three ways.

See metadata per document

In Browse, each metadata field appears as its own column (meta.domain, meta.method, …). If you only see meta.chunk and meta.source, that's because the documents were ingested with only those two fields — the fix is to ingest richer metadata (see the datasets below, which carry fields like domain, method, topic, type).

Metadata summary panel

Open Metadata summary in Browse to see counts per value for every field — e.g. domain: payments (6), cards (5), auth (5)…. This is your first read on a collection's shape: imbalance, unexpected values, or a lone deprecated entry all show up here.

Structured filter (a real where clause)

Pick a field, then choose which values to keep. Studio builds an actual Chroma filter, not a text match:

one value   → where = {"domain": "payments"}
several     → where = {"domain": {"$in": ["payments", "cards"]}}

It defaults to all values selected, so it only narrows once you deselect something — it never hides data by surprise. Collections with no metadata simply don't show the filter.

05 Visualize

Three controls sit in a row: Projection, Dimensions, and Color points by.

ControlOptionsUse it to…
ProjectionPCA · t-SNE · UMAPPCA first (fast, deterministic). t-SNE / UMAP when PCA looks like one blob and you want tighter clusters.
Dimensions2D · 3D2D to read and judge. 3D (rotatable) only to spot-check clusters that look merged in 2D.
Color points by(none) · KMeans cluster · any metadata field Color by a metadata field to see if it matches how the data actually groups; color by KMeans to discover groups the metadata doesn't name.

2D or 3D — which is required?

2D is enough to become expert. It can occasionally make truly separate clusters look merged, so when you're unsure whether two groups are distinct, the reliable check is the silhouette score (a number on the full-dimensional vectors), not a third visual axis. Use 3D as an optional rotate-and-look, not as your judgment tool.

Filter the plot

The Visualize tab has the same metadata filter as Browse — restrict the scatter to, say, method = GET to see only the read endpoints, or one domain at a time.

07 The API discovery use case

A developer asks "which API refunds a payment?" in plain language; the system returns the right endpoint. This is Phase 1: discovery by purpose + endpoint, filtered by domain and method.

The one design idea that makes it work

Embed each endpoint's purpose in plain language ("Refund a previously captured payment…"), not its URL. Developers search by intent, not by path — so the purpose is what must live in the embedded text. domain and method are exact-match facets, so they belong in metadata where you can filter on them, not in the embedded text where they'd add noise.

Load it

  1. Run api_discovery_ingestion_retrieval.ipynb — it ingests the 30 endpoints and prints the database folder path.
  2. In Studio's sidebar, set the Local Chroma folder to that path and select the api_catalog collection.

Explore it in Studio

In StudioDo thisYou should see
Browse → summaryOpen the metadata summary domain spread across 7 services; one deprecated status
Browse → filterKeep only domain = payments 6 endpoints
SearchSearch "refund a payment" pay_refund_01 — POST /v1/payments/{id}/refund — on top
VisualizeColor by domain; then filter method = GET Domains cluster; the GET filter isolates the read-only endpoints
VisualizeLook for stacked points pay_create_01 and pay_create_02 (v1/v2) sit together

The decisions this surfaces

  • Deprecated hygiene: the legacy /v1/login should be excluded from discovery — filter status = active at query time.
  • Versioning: v1 and v2 of "create payment" are near-duplicates — decide whether discovery returns both or only the latest.
  • Collisions: "send a notification" vs "register a webhook" read alike — if the wrong one ranks first, add a discriminating metadata field rather than blaming the model.

Phase 2 (later): add request/response schemas per endpoint so a developer can ask "what fields does the refund endpoint take?" That's a different chunking design (one endpoint → several schema chunks) and will be its own dataset built on this one.

08 The analyze → decide → act loop

The habit that makes Studio more than a viewer. Every view maps to a decision, and every decision is one of a small set.

What a view showsThe decision
A topic/domain with one lone pointEnrich content (thin coverage)
Points stacked on top of each otherDedupe / merge, or filter by version
KMeans clusters disagree with a metadata fieldInvestigate the labels
A point whose label differs from its neighborsFix metadata (no re-embed)
A muddy search resultRe-chunk that document
Top-2 results almost tiedAdd a metadata field to filter on
Blanks in a metadata columnBackfill, then review

The Chroma_Studio_Playbook.ipynb walks this loop on a deliberately flawed dataset — do it once and this table becomes second nature.

09 Troubleshooting

SymptomCause & fix
Lock / connection error on connect Another process holds the folder. Close other notebooks / ChromaFlowStudio; only one process may use a local Chroma folder.
Only meta.chunk / meta.source show up The documents were ingested with just those fields. Re-ingest with richer metadata (see the datasets above), or add fields in Edit/Update (metadata-only, no re-embed).
KeyError: '_type' or schema errors Version mismatch — the database was made by a different Chroma version. Keep your Python on chromadb 1.5.9, and don't open a 1.5.9 database with 0.5.x.
UMAP option errors pip install umap-learn, or use PCA / t-SNE, which need nothing extra.
Add / Search fails on the embedder Check the sidebar embedding source (base URL, API key). Browsing and deleting still work without it.
Chroma Studio targets chromadb 1.5.9. Embeddings default to your in-house Jina endpoint; no external HuggingFace download is required. This guide pairs with the ingestion notebooks and the Studio Playbook for hands-on practice.
