⚠ Security — do this before running anything

The plain-RAG notebook contains live API keys

Building_Conversational_RAG.ipynb has two API keys hardcoded in code cells — an OpenAI-style key and a Google key. A notebook with real keys in it is a credential leak the moment it's shared or committed.

Fix, in order: (1) rotate both keys — revoke the exposed ones and generate new; assume the old ones are compromised. (2) Replace them with environment reads. (3) Keep keys in a git-ignored .env.

import os
openai_key = os.getenv("OPENAI_API_KEY")
google_key = os.getenv("GOOGLE_API_KEY")

The Pinecone and GraphRAG artifacts already do this correctly (os.getenv + .env) — copy their pattern. Same lesson as any credential leak: rotate, remove, and tell whoever owns the accounts if they're organizational.

00 Core concepts (know these before you build)

Each exercise leans on one big idea. Understand these four and the code reads like prose.

Retrieval-Augmented Generation (all three)

An LLM only knows its training data. RAG fixes that by retrieving relevant text from your documents and putting it in the prompt, so the model answers from your content, not its memory. The pipeline is always the same: ingest → chunk → embed → store → retrieve → generate. Everything else is variation on where you store vectors and how you retrieve them.

Chunking & embeddings (all three)

Documents are split into chunks (passages) because you retrieve pieces, not whole files. Each chunk becomes an embedding — a list of numbers capturing its meaning, so "refund a payment" lands near "get my money back" even with no shared words. Retrieval = find the chunks whose embeddings are closest to the question's embedding (cosine similarity).

Hybrid search: dense + sparse + alpha (exercise 2)

Dense vectors (from a neural model) capture meaning. Sparse vectors (BM25) capture exact keywords. Hybrid search fuses both, weighted by alpha: alpha=1 pure meaning, alpha=0 pure keywords, 0.5 a blend. Conceptual questions want high alpha; exact-term lookups (a code, an acronym) want low alpha. Tuning alpha is the core skill exercise 2 teaches.

Graph databases as vector stores (exercise 3)

Neo4j stores data as nodes and relationships. Exercise 3 stores each chunk as a :Chunk node with an embedding property and a vector index for fast similarity search. Note: storing isolated nodes with no relationships is "RAG on a graph database," not true GraphRAG — real GraphRAG links entities across chunks and traverses those links at query time. The extra practice includes turning this into the real thing.

Evaluation with RAGAS (exercises 2 & 3)

How do you know an answer is good without a human checking? RAGAS uses an LLM as judge: Faithfulness (is every claim grounded in the retrieved context?) and Answer Relevancy (does it address the question?), mostly without needing labelled ground truth. It turns "looks fine" into a number you can track across changes.

01 Plain RAG on Chroma

Building_Conversational_RAG.ipynb — the no-framework version. Read file → chunk → embed → store in Chroma → search → feed the LLM. Nothing hidden.

Setup

lab                     # activate your venv (chroma_lab_env)
pip install chromadb PyPDF2 python-docx sentence-transformers google-genai openai
export GOOGLE_API_KEY="your-rotated-key"     # after the security fix

Run it, cell by cell

  1. Install & imports — libraries load; confirm no import errors.
  2. Read the PDF — PyPDF2 extracts text from ERP-2008-chapter4.pdf.
  3. Chunk — text split into passages. Look at a couple to see their size.
  4. Set up Chroma — PersistentClient(path="./chroma_db").
  5. Insert — each chunk embedded (SentenceTransformer) and stored.
  6. Semantic search — a question is embedded; top-K chunks returned.
  7. RAG answer — those chunks go into a prompt; the LLM answers from them.
Observe: after insert, the collection count equals your chunk count. Searching "demand for health" returns the passage from page 2 of the PDF. The final answer uses that content — not invented facts.

Tie-in

This is the notebook form of your Chroma Studio datasets — same loop. Afterward, open ./chroma_db in Chroma Studio and browse/visualize exactly what the notebook stored.

02 Hybrid RAG on Pinecone

Building_Conversational_HybridRAG_Pinecone.ipynb — the strongest exercise. Dense + sparse fusion, conversational memory, and a RAGAS finish.

Setup

pip install pinecone pinecone-text sentence-transformers PyPDF2 google-genai python-dotenv
pip install ragas langchain-google-genai langchain-huggingface datasets   # RAGAS section

Sign up at pinecone.io (free starter tier), create an API key, and put keys in a git-ignored .env:

PINECONE_API_KEY=your-pinecone-key
GOOGLE_API_KEY=your-gemini-key

Org-network note: Pinecone is cloud-hosted. If your org blocks it, run this exercise from a personal machine.

Work through the steps

  1. Load & chunk the PDF (steps 2–3 in the notebook).
  2. Dense embeddings — SentenceTransformer vectors (meaning).
  3. Sparse embeddings — BM25 vectors (keywords).
  4. Create the Pinecone index and upsert hybrid vectors.
  5. Hybrid search with alpha — the heart of the exercise (see below).
  6. Conversational memory — a follow-up resolves using prior turns.
  7. RAGAS validation — faithfulness + answer relevancy scores.

Spend your time on the alpha knob

Run the same query at alpha = 0.0, 0.5, and 1.0 and watch the retrieved chunks change. Keyword-heavy queries (an exact term like "Medicare Part D") do better at low alpha; conceptual queries ("why do costs rise?") do better at high alpha. This trade-off is the whole point.

Observe: at step 8, alpha visibly reorders results. At step 10, the bot answers a follow-up ("what about its cost?") by remembering the prior question. At step 11, faithfulness near 1.0 means the answer is grounded.

Tie-in

The dense+sparse fusion is the hybrid-search concept from Specialist Track Phase 5 and hybrid_search.py in your Week 15 pipeline. The RAGAS section is your ragas_guide applied live.

03 Graph-DB RAG on Neo4j

GraphRAG/ — a full multi-file app with a Gradio UI. The most "real project" of the three. Clean separation: config / pdf_processor / embeddings / vector_store / response_generator / validator / orchestrator / app.

Read the honest label

Despite the name, this stores isolated :Chunk nodes with embeddings and does cosine search — no relationships between nodes. It's an excellent way to learn Neo4j + vector indexes, but it's not relationship-aware GraphRAG. Extra-practice exercise 4 turns it into the real thing.

Python setup

lab
cd GraphRAG
pip install -r requirements.txt

First-run HuggingFace note: all-mpnet-base-v2 (~420 MB) downloads from HuggingFace on first use. If your org blocks HF, download it once on a personal network (it caches to ~/.cache/huggingface) — the same HF-blocking issue you hit with ChromaFlowStudio.

Run

  1. Set up Neo4j (next section) and fill in .env.
  2. python app.py → Gradio prints a local URL (usually http://127.0.0.1:7860).
  3. Upload tab — upload the PDF; watch the console chunk → embed → store.
  4. Query tab — ask "What is the demand for health?"
  5. Validate tab — RAGAS scores the answer.
  6. Manage tab — document/chunk counts; delete a document.
Observe: the Manage-tab chunk count matches what you uploaded. An off-topic question should get "I can't find that in the documents," not a hallucination. Faithfulness is high for grounded answers.

3·db Neo4j setup (the graph database)

The one piece of infrastructure exercise 3 needs. Pick whichever option fits — Desktop is easiest for local practice.

Option A — Neo4j Desktop (recommended for local)

  1. Download from neo4j.com/download, install, open.
  2. New project → Add a Local DBMS; set a password (goes in .env); pick a 5.x version (needed for the vector index).
  3. Click Start. It listens on bolt://localhost:7687.
  4. Optionally open Neo4j Browser to run Cypher and watch your data.

Option B — Docker (clean & reproducible)

docker run -d --name neo4j-rag \
  -p 7474:7474 -p 7687:7687 \
  -e NEO4J_AUTH=neo4j/your-password-here \
  -e NEO4J_PLUGINS='["apoc"]' \
  neo4j:5.23

7474 = Neo4j Browser (http://localhost:7474); 7687 = Bolt (what the app connects to).

Option C — Neo4j Aura (free cloud)

If you can't install locally: create a free instance at neo4j.com/cloud/aura and use the URI/credentials it gives you. Cloud, so same org-network caveat as Pinecone.

The database-name gotcha

The app defaults to a database named graphragdb, but Neo4j Community Edition only gives you the default neo4j database. Easiest fix: set NEO4J_DATABASE=neo4j in .env. (On Enterprise/Aura you can CREATE DATABASE graphragdb in the browser instead.)

Fill in .env

NEO4J_URI=bolt://localhost:7687
NEO4J_USER=neo4j
NEO4J_PASSWORD=your-password-here
NEO4J_DATABASE=neo4j
GEMINI_API_KEY=your-gemini-key
HF_TOKEN=your-hf-token          # optional; only for gated HF models

See your data (the fun part)

After uploading a PDF, run this in Neo4j Browser — the graph-DB equivalent of Chroma Studio's Browse tab:

MATCH (c:Chunk) RETURN c.source, c.chunk_index, c.text LIMIT 25;
MATCH (c:Chunk) RETURN count(c);

The vector index

On startup, vector_store.py creates a vector index on Chunk.embedding (768-dim, cosine). This needs Neo4j 5.11+; on older versions it silently falls back to manual cosine in Cypher (works, slower). Use 5.x to get the real index.

+ Extra practice exercises

Each targets a concept the three files don't fully exercise. Ordered roughly easy → ambitious. Do them on the same PDF so results are comparable.

Exercise A · Chunking

Compare three chunking strategies

The plain-RAG notebook uses one chunking method. Re-ingest the PDF three ways — fixed-size (e.g. 200 words), sentence-based, and fixed-size with 20% overlap — into three Chroma collections. Ask the same question against each and compare which returns the cleanest supporting chunk.

What you learn: chunking decides retrieval quality more than any other single factor. Overlap rescues answers that sit on a chunk boundary. ties to Specialist Track Phase 2

Exercise B · Hybrid tuning

Turn the alpha knob into a scored sweep

The Pinecone notebook lets you set alpha by hand. Instead, write 5 test questions (some keyword-y like "Medicare Part D", some conceptual like "why do costs rise"), then loop alpha over [0, 0.25, 0.5, 0.75, 1.0] and score each with RAGAS faithfulness + answer relevancy. Plot score vs alpha.

What you learn: the best alpha isn't a guess — it's measurable, and it differs by query type. This is data-driven tuning. ties to ragas_guide

Exercise C · Metadata-filtered RAG

Filter by section before retrieving

Tag each chunk with the PDF section it came from (e.g. "Health Insurance", "Moral Hazard", "Medicare") as metadata. Then answer a question restricted to one section using Chroma's where filter before semantic search.

What you learn: metadata filtering scopes retrieval and kills cross-section noise — exactly the Chroma Studio filtering you built, applied to RAG. ties to Chroma Studio metadata features

Exercise D · Cross-store comparison

Same query, Chroma vs Neo4j

Ingest the identical chunks + embeddings into both Chroma (exercise 1) and Neo4j (exercise 3). Run the same five questions against each and compare the top-K retrieved. They should mostly agree — where they differ, dig into why (index type, similarity computation).

What you learn: the vector store is swappable; retrieval quality comes from embeddings + chunking, not the database brand. systems intuition

Exercise E · Real GraphRAG

Add entities and relationships to the Neo4j app

Turn the graph-DB app into genuine GraphRAG: (1) extract entities from each chunk (Medicare, HSA, moral hazard, …) into :Entity nodes; (2) link them — (:Chunk)-[:MENTIONS]->(:Entity) and (:Entity)-[:RELATED_TO]->(:Entity); (3) at query time, retrieve by vector and traverse relationships to pull in connected context (multi-hop).

What you learn: what "graph" actually adds over plain vector RAG — relationship-aware, multi-hop retrieval. This is the real thing. the ambitious one · ties to Specialist Track multi-hop

Exercise F · RAGAS-driven tuning loop

Change one thing, measure, repeat

Pick any single knob — chunk size, top-K, or alpha — and run a controlled experiment: baseline RAGAS scores, change the knob, re-score, compare. Never ship a change you can't show helped.

What you learn: the professional RAG workflow — measure → change → re-measure — rather than tweaking on vibes. the meta-skill
