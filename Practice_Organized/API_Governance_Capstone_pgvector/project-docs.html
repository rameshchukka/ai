Software Requirements Specification (Final)

Mule API Redundancy Detection & Composition Advisory Platform

Audience: Engineering team Status: Implementation-ready Supersedes: all prior SRS drafts and the standalone composition DB addendum — fully merged here

1. Introduction

1.1 Purpose

This SRS defines the technical design for a system with two complementary goals:

  1. Redundancy detection — build a call graph of all Mule APIs (Exp/Proc/Sys layers), detect structurally redundant or unnecessary hops (Phase 1), and confirm which findings are safe to act on using traffic and functional-purpose signals (Phase 2).
  2. Composition advisory — given a new requirement, determine whether an existing API satisfies it directly, whether existing APIs can be composed/orchestrated to satisfy it, or whether new development is genuinely needed — backed by structural schema-compatibility checking, not similarity scores alone.

Both goals share the same Foundation data (Section 3) and vector store (Section 4).

1.2 Scope

In scope: - Graph construction, traversal (max 5 hops), Phase 1 structural rules - Relational + vector data design for both redundancy and composition use cases - Traffic/P95 ingestion, LLM-assisted functional matching (Phase 2) - Field-level schema capture and compatibility scoring (composition validator) - Streamlit application across both use cases - All outputs are recommendations requiring human approval — nothing executes automatically against production APIs

Out of scope (this phase): - Automatic retirement, merging, or code changes to any API - Actually executing composed API calls against production systems — this system recommends a composition; it does not orchestrate live traffic - A public-facing or multi-team-consumed REST API - CI/CD integration for continuous graph refresh

1.3 Definitions

Term Definition
Node One API (Exp, Proc, or Sys layer) represented as a graph vertex
Edge A directed call from one API to another, with specific endpoint paths on both sides
Flow A complete path from an Exp node to its terminal Sys node(s), 3–5 hops typical
Pass-through hop A Proc node with exactly one outbound edge and no orchestration logic
Fan-in A node with high in-degree — many distinct callers converging on it
Merge candidate Two APIs flagged as functionally redundant — candidate for retiring one
Composition candidate One or more APIs proposed as a chain to satisfy a new requirement — not redundant, complementary
Field mapping A precomputed match between one API's response field and another API's request field

2. System Overview

┌──────────────────────────────────────────────────────────────────┐
│  FOUNDATION                                                       │
│  api_nodes, api_edges  +  api_fields (structured field rows)      │
│  + node_embeddings (pgvector)  — all in one PostgreSQL instance   │
├──────────────────────────────────────────────────────────────────┤
│  PHASE 1 — Structural Analysis (redundancy)                       │
│  Recursive CTE traversal → 4 structural rules → structural_findings│
├──────────────────────────────────────────────────────────────────┤
│  PHASE 1.5 — Schema Compatibility (composition foundation)        │
│  field_mappings precomputation → reusable by composition checks    │
├──────────────────────────────────────────────────────────────────┤
│  PHASE 2 — Traffic, Functional & Composition Confirmation         │
│  Traffic ingestion → embeddings → merge scoring                   │
│  → composition scoring (similarity + schema compat + domain)      │
├──────────────────────────────────────────────────────────────────┤
│  APPLICATION (Streamlit)                                          │
│  Graph Explorer, Findings, Merge Candidates, Impact Analysis,     │
│  Composition Advisor, Embedding Health — all call core/ directly  │
└──────────────────────────────────────────────────────────────────┘

Why "Phase 1.5" exists as its own layer: field mapping precomputation depends on structured field data existing (Foundation) but does not depend on traffic or LLM calls (Phase 2's other dependencies). It's structural, like Phase 1, but specific to the composition use case rather than redundancy. Keeping it separate avoids conflating "this API is redundant" logic with "this API can feed data into that API" logic — they answer different questions and feed different output tables.

See 02-architecture.md for the full stack reasoning (Streamlit vs Flask/React, PostgreSQL CTE vs Neo4j, no GraphQL, pgvector inside PostgreSQL, UMAP vs t-SNE).

3. Relational Database Design (Complete)

3.1 api_nodes

CREATE TABLE api_nodes (
    node_id             SERIAL PRIMARY KEY,
    project_name        VARCHAR(255) NOT NULL,
    layer               VARCHAR(10) NOT NULL,        -- 'exp' | 'proc' | 'sys'
    listener_endpoint   VARCHAR(500),
    functionality       VARCHAR(255),                 -- e.g. 'NACH Debit', 'E-Mandate Debit'
    domain              VARCHAR(100),                 -- e.g. 'payments', 'mandate'
    purpose_text        TEXT,
    owning_team         VARCHAR(100),
    status              VARCHAR(20) DEFAULT 'active', -- active | merged | retired
    merged_into         INT REFERENCES api_nodes(node_id),
    created_at          TIMESTAMPTZ DEFAULT NOW(),
    CHECK (layer IN ('exp','proc','sys'))
);

CREATE INDEX idx_nodes_functionality ON api_nodes(functionality);
CREATE INDEX idx_nodes_domain        ON api_nodes(domain);

functionality is deliberately separate from domain — domain is broad ("payments"), functionality is specific ("NACH Debit" vs "E-Mandate Debit"). This distinguishes two APIs in the same domain that are NOT redundant.

3.2 api_edges

CREATE TABLE api_edges (
    edge_id               SERIAL PRIMARY KEY,
    source_node_id         INT NOT NULL REFERENCES api_nodes(node_id),
    target_node_id         INT NOT NULL REFERENCES api_nodes(node_id),
    source_project_name    VARCHAR(255),
    target_project_name    VARCHAR(255),
    source_endpoint_path   VARCHAR(500),
    target_endpoint_path   VARCHAR(500),
    call_type              VARCHAR(20) DEFAULT 'sync',  -- sync | async
    discovered_at          TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(source_node_id, target_node_id, source_endpoint_path, target_endpoint_path)
);

CREATE INDEX idx_edges_source ON api_edges(source_node_id);
CREATE INDEX idx_edges_target ON api_edges(target_node_id);

Endpoint paths are stored on the edge, not just node-to-node, because one Proc API often has multiple endpoints calling different downstream paths — needed for precise impact analysis (Section 9).

3.3 api_fields — structured, field-level (required for composition)

CREATE TABLE api_fields (
    field_id        SERIAL PRIMARY KEY,
    node_id         INT NOT NULL REFERENCES api_nodes(node_id),
    direction       VARCHAR(10) NOT NULL,        -- 'request' | 'response'
    field_path      VARCHAR(255) NOT NULL,       -- e.g. 'customer.customer_id'
    field_name      VARCHAR(100) NOT NULL,       -- leaf name, e.g. 'customer_id'
    data_type       VARCHAR(30),                  -- string | integer | boolean | object | array | date
    is_required     BOOLEAN DEFAULT FALSE,
    description     TEXT,
    sample_value    TEXT,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    CHECK (direction IN ('request', 'response'))
);

CREATE INDEX idx_fields_node      ON api_fields(node_id);
CREATE INDEX idx_fields_name      ON api_fields(field_name);
CREATE INDEX idx_fields_direction ON api_fields(node_id, direction);

This is the table that makes composition possible. Without per-field rows, there's no way to check whether API A's response field matches API B's required request field except by re-reading prose every time. This must be populated at initial ingestion (Section 6.2 of 01-srs.md / Milestone M3) — retrofitting it after hundreds of APIs are ingested without structured fields means re-extracting from source for all of them.

3.4 field_mappings — precomputed compatibility

CREATE TABLE field_mappings (
    mapping_id          SERIAL PRIMARY KEY,
    source_field_id      INT NOT NULL REFERENCES api_fields(field_id),  -- a response field
    target_field_id      INT NOT NULL REFERENCES api_fields(field_id),  -- a request field
    match_type           VARCHAR(20),       -- 'exact_name' | 'fuzzy_name' | 'semantic' | 'manual'
    match_confidence      DECIMAL(5,4),
    type_compatible       BOOLEAN,
    verified_by_human      VARCHAR(100),
    created_at            TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(source_field_id, target_field_id)
);

CREATE INDEX idx_mappings_source ON field_mappings(source_field_id);
CREATE INDEX idx_mappings_target ON field_mappings(target_field_id);

Computed once per field pair (batch job, Milestone M5), not recalculated per user query — keeps composition lookups fast as the dataset grows.

3.5 Flow, findings, and merge tables (redundancy use case)

CREATE TABLE flows (
    flow_id          SERIAL PRIMARY KEY,
    root_exp_id      INT NOT NULL REFERENCES api_nodes(node_id),
    node_path        INT[] NOT NULL,
    endpoint_path    TEXT[],
    hop_count        INT NOT NULL,
    terminal_sys_id  INT REFERENCES api_nodes(node_id),
    built_at         TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE structural_findings (
    finding_id      SERIAL PRIMARY KEY,
    pattern_type    VARCHAR(40) NOT NULL,
      -- 'DUPLICATE_FLOW' | 'PASS_THROUGH_HOP' | 'DEEP_CHAIN' | 'FAN_IN_CLUSTER'
    node_ids        INT[] NOT NULL,
    severity        VARCHAR(10),
    detail          JSONB,
    detected_at     TIMESTAMPTZ DEFAULT NOW(),
    review_status   VARCHAR(20) DEFAULT 'open'
);

CREATE TABLE merge_candidates (
    candidate_id        SERIAL PRIMARY KEY,
    node_a_id           INT NOT NULL REFERENCES api_nodes(node_id),
    node_b_id           INT NOT NULL REFERENCES api_nodes(node_id),
    structural_score    DECIMAL(5,4),
    semantic_score      DECIMAL(5,4),
    traffic_risk        VARCHAR(10),
    recommendation      VARCHAR(20),
    confidence          VARCHAR(10),
    llm_rationale       TEXT,
    status              VARCHAR(20) DEFAULT 'pending',
    created_at          TIMESTAMPTZ DEFAULT NOW(),
    CHECK (node_a_id < node_b_id)
);

3.6 composition_candidates — orchestration findings (composition use case)

CREATE TABLE composition_candidates (
    composition_id              SERIAL PRIMARY KEY,
    requirement_text            TEXT NOT NULL,
    node_sequence                INT[] NOT NULL,           -- ordered chain of node_ids
    similarity_score              DECIMAL(5,4),
    schema_compatibility_score    DECIMAL(5,4),
    domain_alignment_score        DECIMAL(5,4),
    composition_confidence        DECIMAL(5,4),
    recommendation                VARCHAR(20),              -- DIRECT_MATCH | COMPOSE | NEW_BUILD
    llm_rationale                  TEXT,
    status                         VARCHAR(20) DEFAULT 'proposed',  -- proposed | approved | rejected
    created_at                     TIMESTAMPTZ DEFAULT NOW()
);

Kept separate from merge_candidates — a merge candidate says "these are redundant, retire one." A composition candidate says "chain these in this order to satisfy a new requirement." Different relationship, different review workflow.

3.7 Traffic metrics (Phase 2, shared by both use cases)

CREATE TABLE traffic_metrics (
    metric_id       SERIAL PRIMARY KEY,
    node_id         INT NOT NULL REFERENCES api_nodes(node_id),
    measured_date   DATE NOT NULL,
    daily_hits      BIGINT DEFAULT 0,
    p95_latency_ms  DECIMAL(8,2),
    p99_latency_ms  DECIMAL(8,2),
    UNIQUE(node_id, measured_date)
);

CREATE VIEW node_traffic_summary AS
SELECT node_id,
       AVG(daily_hits)      AS avg_daily_hits,
       AVG(p95_latency_ms)  AS avg_p95_ms,
       MAX(daily_hits)      AS peak_daily_hits
FROM traffic_metrics
WHERE measured_date >= CURRENT_DATE - INTERVAL '30 days'
GROUP BY node_id;

3.8 audit_log — shared across both use cases

CREATE TABLE audit_log (
    log_id          SERIAL PRIMARY KEY,
    entity_type     VARCHAR(30),      -- 'finding' | 'merge_candidate' | 'composition_candidate'
    entity_id       INT NOT NULL,
    action          VARCHAR(30),      -- 'reviewed' | 'dismissed' | 'approved' | 'rejected' | 'deferred'
    comment         TEXT,
    reviewer        VARCHAR(100),
    acted_at        TIMESTAMPTZ DEFAULT NOW()
);

3.8b llm_call_log — every LLM call logged for auditability

CREATE TABLE llm_call_log (
    call_id         SERIAL PRIMARY KEY,
    call_type       VARCHAR(40) NOT NULL,
      -- 'query_expansion' | 'field_equivalence' | 'composition_decision'
      -- | 'discovery_review' | 'merge_rationale'
    entity_id       INT,            -- node_id, candidate_id, or composition_id if applicable
    system_prompt   TEXT,
    user_prompt     TEXT,
    llm_response    TEXT,
    tokens_used     INT,
    latency_ms      INT,
    called_at       TIMESTAMPTZ DEFAULT NOW()
);

Every LLM call — query expansion, field equivalence, composition decision, discovery quick-take — writes a row here before returning. This is what makes "why did the system recommend X" answerable after the fact. See 07-llm-integration-guide.md for the full integration design.

3.9 Supporting tables (operational completeness at real scale)

The tables in Sections 3.1–3.8 are sufficient for a sample dataset, but at ~3,000 nodes ingested from ~2,000+ Bitbucket repos on a recurring schedule, several operational gaps become real correctness risks, not just nice-to-haves. Each subsection below explains the specific risk it closes.

3.9.1 source_repos — ingestion source tracking

Risk closed: without this, there's no way to trace a wrong/missing node back to the repo that produced it, or to re-run extraction for one repo without re-scanning everything.

CREATE TABLE source_repos (
    repo_id         SERIAL PRIMARY KEY,
    repo_name       VARCHAR(255) NOT NULL UNIQUE,
    repo_url        VARCHAR(500),
    last_scanned_at TIMESTAMPTZ,
    last_commit_sha VARCHAR(64),        -- detect if repo changed since last scan
    extraction_status VARCHAR(20) DEFAULT 'pending',  -- pending | success | failed | partial
    extraction_error  TEXT,             -- populated if status = 'failed'/'partial'
    node_id           INT REFERENCES api_nodes(node_id),  -- the node this repo produced, once known
    created_at        TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_source_repos_status ON source_repos(extraction_status);

3.9.2 ingestion_runs — batch run metadata

Risk closed: without this, a failed or partial ingestion run is invisible — you'd only discover it later as "missing data," with no record of when or why.

CREATE TABLE ingestion_runs (
    run_id            SERIAL PRIMARY KEY,
    run_type          VARCHAR(30) NOT NULL,  -- 'full_scan' | 'incremental' | 'field_mapping_refresh'
    started_at        TIMESTAMPTZ DEFAULT NOW(),
    completed_at      TIMESTAMPTZ,
    repos_scanned     INT DEFAULT 0,
    repos_succeeded   INT DEFAULT 0,
    repos_failed      INT DEFAULT 0,
    nodes_created     INT DEFAULT 0,
    nodes_updated     INT DEFAULT 0,
    edges_created     INT DEFAULT 0,
    status            VARCHAR(20) DEFAULT 'running',  -- running | completed | failed
    error_summary     TEXT
);

Every milestone from M1 onward that touches ingestion (M1, M3, M5, M11) should write a row here. This becomes the single place to answer "is the graph up to date, and when did it last fail" — exactly the question a reviewer asks before trusting a finding.

3.9.3 api_versions — version-aware node identity

Risk closed: without this, proc-order-api-v1 and proc-order-api-v2 look like two unrelated nodes — risking a false DUPLICATE_FLOW finding (Phase 1) between two versions of the same API, which is not redundancy, just normal versioning.

CREATE TABLE api_versions (
    version_id      SERIAL PRIMARY KEY,
    node_id         INT NOT NULL REFERENCES api_nodes(node_id),
    version_label   VARCHAR(20) NOT NULL,    -- e.g. 'v1', 'v2', '2024-03'
    is_current      BOOLEAN DEFAULT TRUE,
    superseded_by   INT REFERENCES api_versions(version_id),
    released_at     TIMESTAMPTZ,
    deprecated_at   TIMESTAMPTZ,
    UNIQUE(node_id, version_label)
);

Add a check in the duplicate-flow rule (Section 6.2): before flagging two nodes as a duplicate, confirm they aren't different api_versions rows of the same node_id lineage. This is a one-line guard, but without the table to check against, there's nothing to guard with.

3.9.4 domain_taxonomy and functionality_taxonomy — controlled vocabulary

Risk closed: api_nodes.domain and .functionality are free-text today. If one ingested API is tagged "payments" and another "Payments" (case) or "payment" (singular), domain-alignment scoring (Section 5.3) and fan-in clustering (Section 6.2) silently fragment — two genuinely related APIs won't be recognized as the same domain, undercounting findings without any visible error.

CREATE TABLE domain_taxonomy (
    domain_id       SERIAL PRIMARY KEY,
    domain_name     VARCHAR(100) NOT NULL UNIQUE,   -- canonical form, e.g. 'payments'
    description     TEXT,
    parent_domain_id INT REFERENCES domain_taxonomy(domain_id)  -- optional hierarchy
);

CREATE TABLE functionality_taxonomy (
    functionality_id   SERIAL PRIMARY KEY,
    functionality_name VARCHAR(255) NOT NULL UNIQUE,  -- canonical form, e.g. 'NACH Debit'
    domain_id           INT REFERENCES domain_taxonomy(domain_id),
    description          TEXT
);

-- api_nodes.domain and .functionality become foreign keys, not free text:
ALTER TABLE api_nodes
    ADD COLUMN domain_id         INT REFERENCES domain_taxonomy(domain_id),
    ADD COLUMN functionality_id  INT REFERENCES functionality_taxonomy(functionality_id);
-- the original VARCHAR columns are retained during migration for backward
-- compatibility, then dropped once all rows are mapped (see Milestone M1b)

At ingestion time, the LLM-driven extraction step (the same one that produces purpose_text) should map its raw domain guess to the closest existing domain_taxonomy entry, or flag a new-domain request for human review rather than silently creating a new free-text variant. This is a small addition to the existing extraction prompt, not a new system.

3.9.5 team_directory — normalized ownership

Risk closed: owning_team as free text makes "show me all redundant APIs owned by Team X" an unreliable text match. A normalized table makes ownership-based reporting (a natural ask once findings exist) a clean join instead of fuzzy text matching.

CREATE TABLE team_directory (
    team_id         SERIAL PRIMARY KEY,
    team_name       VARCHAR(100) NOT NULL UNIQUE,
    department      VARCHAR(100),
    contact_channel VARCHAR(255)     -- e.g. a Slack channel or distribution list
);

ALTER TABLE api_nodes
    ADD COLUMN team_id INT REFERENCES team_directory(team_id);

3.9.6 api_specs — raw source storage

Risk closed: without storing the raw OpenAPI/Swagger spec (or whatever source document produced a node), there is no way to re-parse an API if the extraction prompt improves later, or to manually verify what the LLM extraction was based on when a finding looks wrong.

CREATE TABLE api_specs (
    spec_id         SERIAL PRIMARY KEY,
    node_id         INT NOT NULL REFERENCES api_nodes(node_id),
    spec_format     VARCHAR(20),       -- 'openapi' | 'raml' | 'markdown' | 'other'
    raw_content     TEXT,               -- the actual spec/doc source
    source_repo_id  INT REFERENCES source_repos(repo_id),
    ingested_at     TIMESTAMPTZ DEFAULT NOW(),
    extraction_run_id INT REFERENCES ingestion_runs(run_id)
);

This is what lets you re-run M3's structured-field extraction later with an improved prompt, without re-scanning Bitbucket — the raw source is already here.

3.9.7 edge_history — edge lifecycle tracking

Risk closed: api_edges currently only has discovered_at. If an API stops calling another (the calling code is removed), the current design either leaves a stale edge forever or deletes it with no record — both bad for a governance tool where "this used to call that, but doesn't anymore" is itself useful information (e.g. confirms a past pass-through hop was actually removed).

CREATE TABLE edge_history (
    history_id      SERIAL PRIMARY KEY,
    source_node_id   INT NOT NULL REFERENCES api_nodes(node_id),
    target_node_id   INT NOT NULL REFERENCES api_nodes(node_id),
    source_endpoint_path VARCHAR(500),
    target_endpoint_path VARCHAR(500),
    event_type       VARCHAR(20) NOT NULL,   -- 'appeared' | 'disappeared'
    detected_in_run  INT REFERENCES ingestion_runs(run_id),
    event_at         TIMESTAMPTZ DEFAULT NOW()
);

api_edges itself stays as the current state (what the graph looks like now). edge_history is the append-only log of changes — this is what M11's refresh job writes to when it detects a diff between runs.

3.9.8 graph_snapshots — versioned findings

Risk closed: flows and structural_findings currently have no link to which run produced them. Once M11's weekly refresh is live, there's no way to answer "show me what the graph looked like last Tuesday" or "did this finding exist before last week's change" without this.

CREATE TABLE graph_snapshots (
    snapshot_id     SERIAL PRIMARY KEY,
    run_id          INT NOT NULL REFERENCES ingestion_runs(run_id),
    node_count      INT,
    edge_count      INT,
    taken_at        TIMESTAMPTZ DEFAULT NOW()
);

-- flows and structural_findings gain a snapshot reference:
ALTER TABLE flows              ADD COLUMN snapshot_id INT REFERENCES graph_snapshots(snapshot_id);
ALTER TABLE structural_findings ADD COLUMN snapshot_id INT REFERENCES graph_snapshots(snapshot_id);

This is what makes M11's "new / resolved / persisting" diff (per 04-milestones.md M11) actually queryable — without a snapshot_id to group by, "compare this run to the last run" has no clean boundary to compare across.

4. Vector Database Design (pgvector inside PostgreSQL)

All embedding storage and similarity search lives in the same PostgreSQL instance as the relational tables in Section 3, using the pgvector extension. No second database to operate. See 02-architecture.md Section 5 for the full reasoning and index choice.

4.1 Schema

-- Enable the extension (once per database)
CREATE EXTENSION IF NOT EXISTS vector;

-- One row per chunk per API node
-- chunk_type: 'purpose' | 'business_rules' | 'request_fields' | 'response_fields'
CREATE TABLE node_embeddings (
    embedding_id  SERIAL PRIMARY KEY,
    node_id       INT NOT NULL REFERENCES api_nodes(node_id),
    chunk_type    VARCHAR(30) NOT NULL,
    embed_text    TEXT NOT NULL,           -- the exact text that was embedded (for audit)
    embedding     VECTOR(1536),            -- 1536 = text-embedding-3-small dimension
    updated_at    TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(node_id, chunk_type)
);

-- HNSW index — best for production query speed
-- Build once after bulk insert; cosine distance matches the retrieval queries below
CREATE INDEX idx_node_emb_hnsw
    ON node_embeddings
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- Alternative: IVFFlat (faster to build, use during dev/sample-data phase)
-- CREATE INDEX idx_node_emb_ivf
--     ON node_embeddings
--     USING ivfflat (embedding vector_cosine_ops)
--     WITH (lists = 100);   -- rule of thumb: sqrt(expected row count)

Choosing 1536 vs other dimensions: 1536 matches OpenAI's text-embedding-3-small. If you use an internal LLM embedding model with a different dimension (e.g. 768, 1024, 3072), change VECTOR(1536) to match it — you cannot mix dimensions in one column. Check the dimension of whichever embedding endpoint you already use internally before creating the table.

4.2 Chunking strategy

Field(s) Chunk type Embedded? Why
API Overview + Business Purpose purpose ✅ Yes Core "what is this for" — primary input for redundancy detection and composition matching
Business Rules business_rules ✅ Yes Logic-level signal; used for composition domain alignment
Request Parameters + Body Fields request_fields ✅ Yes (prose) + structured api_fields rows Prose for semantic search; structured rows for exact field compatibility checks
Response Fields response_fields ✅ Yes (prose) + structured api_fields rows Same dual treatment as above
Endpoint & HTTP Method — ❌ Metadata only Exact-match data — belongs in api_nodes.listener_endpoint, not an embedding
Headers & Authentication — ❌ Metadata only Mostly categorical; doesn't benefit from semantic search
Error Codes — ❌ Metadata only Categorical lookups
Sample Request/Response — ❌ Not stored in embeddings Adds noise; kept in api_specs.raw_content for traceability

Critical note: request/response fields have two representations — the prose chunk (embedded into node_embeddings) and structured rows in api_fields (Section 3.3). Both come from the same source document in the same ingestion pass and serve different purposes: prose for retrieval, structured rows for compatibility. See Section 4.4 for how ingestion writes both.

4.3 Retrieval — four use cases with real SQL

Use case 1: Functional redundancy (find APIs similar to node X)

-- Find the top-5 APIs most similar in purpose to node 42,
-- excluding itself, active only
SELECT
    n.node_id,
    n.project_name,
    n.domain,
    n.functionality,
    1 - (e.embedding <=> target.embedding) AS similarity_score
FROM node_embeddings e
JOIN api_nodes n ON n.node_id = e.node_id
CROSS JOIN (
    SELECT embedding
    FROM node_embeddings
    WHERE node_id = 42 AND chunk_type = 'purpose'
) target
WHERE e.chunk_type = 'purpose'
  AND e.node_id <> 42
  AND n.status = 'active'
ORDER BY e.embedding <=> target.embedding   -- <=> is cosine distance (lower = more similar)
LIMIT 5;

Use case 2: New requirement → existing API (compose or direct match)

-- Embed the requirement text in Python, then pass the vector here
-- :req_embedding is the Python list cast to ::vector
SELECT
    n.node_id,
    n.project_name,
    n.domain,
    n.layer,
    1 - (e.embedding <=> :req_embedding::vector) AS similarity_score
FROM node_embeddings e
JOIN api_nodes n ON n.node_id = e.node_id
WHERE e.chunk_type = 'purpose'
  AND n.status = 'active'
ORDER BY e.embedding <=> :req_embedding::vector
LIMIT 5;

Use case 3: Change impact analysis (field-level semantic impact)

-- Find APIs that reference the same field concept as a proposed change
-- Useful when a field rename could affect APIs not graph-connected to the changed node
SELECT
    n.node_id,
    n.project_name,
    e.chunk_type,
    1 - (e.embedding <=> :change_embedding::vector) AS similarity_score
FROM node_embeddings e
JOIN api_nodes n ON n.node_id = e.node_id
WHERE e.chunk_type IN ('request_fields', 'response_fields')
  AND n.status = 'active'
ORDER BY e.embedding <=> :change_embedding::vector
LIMIT 10;

def numeric_cluster_check(embeddings: np.ndarray, domains: list[str]) -> dict:
    """Within-domain similarity should be clearly higher than cross-domain."""
    sim_matrix = cosine_similarity(embeddings)
    within, across = [], []
    for i in range(len(domains)):
        for j in range(i + 1, len(domains)):
            (within if domains[i] == domains[j] else across).append(sim_matrix[i][j])
    return {
        "within": round(float(np.mean(within)), 3),
        "across": round(float(np.mean(across)), 3),
        "gap":    round(float(np.mean(within) - np.mean(across)), 3)
    }

5.2 Field mapping computation

def compute_field_mappings(source_node_id: int, target_node_id: int, conn) -> list[dict]:
    """For a proposed A -> B chain: does A's response satisfy B's required request fields?"""
    source_fields = get_fields(conn, source_node_id, direction='response')
    target_fields = get_fields(conn, target_node_id, direction='request')

    mappings = []
    for tf in target_fields:
        best_match, best_score = None, 0.0
        for sf in source_fields:
            if sf['field_name'] == tf['field_name']:
                score, match_type = 1.0, 'exact_name'
            elif fuzzy_match(sf['field_name'], tf['field_name']) > 0.8:
                score, match_type = 0.75, 'fuzzy_name'
            else:
                continue

            type_ok = types_compatible(sf['data_type'], tf['data_type'])
            if not type_ok:
                score *= 0.5

            if score > best_score:
                best_score = score
                best_match = {'source_field': sf, 'match_type': match_type,
                              'confidence': score, 'type_compatible': type_ok}

        mappings.append({
            'target_field': tf, 'match': best_match,
            'satisfied': best_match is not None and best_match['confidence'] >= 0.7,
            'required_but_unsatisfied': tf['is_required'] and (best_match is None or best_match['confidence'] < 0.7)
        })
    return mappings


def schema_compatibility_score(mappings: list[dict]) -> float:
    """Fraction of REQUIRED target fields with a satisfied mapping.
    Unmapped optional fields don't penalize the score."""
    required = [m for m in mappings if m['target_field']['is_required']]
    if not required:
        return 1.0
    satisfied = [m for m in required if m['satisfied']]
    return len(satisfied) / len(required)

2. Graph traversal: PostgreSQL recursive CTE, not Neo4j

Decision

Use a recursive CTE in PostgreSQL for all graph traversal (flow building, impact analysis). No graph database.

Reasoning

  • Neo4j's advantage appears at very large graphs (100K+ nodes) or unbounded/deep traversals where recursive joins become slow
  • At ~3,000 nodes with a hard 5-hop cap, a recursive CTE returns in single-digit milliseconds
  • Running Neo4j means operating a second database for zero measurable performance gain at this scale

When to revisit

  • Node count grows past ~50,000
  • Traversal depth requirements become unbounded or highly variable
  • Query patterns start requiring graph-native operations (shortest path across thousands of nodes, community detection) that SQL recursive CTEs handle poorly

3. Composition validator: a core/ module, not a separate service

Decision

The schema-compatibility engine (field mapping, composite scoring, band recommendation) lives in core/composition.py — a Python module called directly by Streamlit, exactly like the redundancy-detection logic. It is not a microservice, not a separate deployable, and does not run as an agent loop that executes API calls.

Reasoning

  • The composition validator's job is to score and recommend, not to execute. It reads api_fields and field_mappings (precomputed, Section 3.4 of 01-srs.md) and returns a confidence score — this is the same shape of work as the merge-candidate scoring already in the system, just with a different formula and different input tables
  • Running this as a separate service (e.g. a LangGraph agent loop with retry/execute semantics) would be solving a problem this project doesn't have: nothing in this system sends live requests to production Mule APIs. Every output is a recommendation a human reviews in the Composition Advisor screen
  • Keeping it as a plain Python module means it's testable the same way the Phase 1 rules are tested — call the function, compare output to a known-correct sample, no infrastructure required to validate logic changes

What this explicitly does NOT do

  • Does not execute HTTP calls against any API, Mule or otherwise
  • Does not have a retry/self-correction loop reacting to live HTTP error codes
  • Does not need an orchestration framework (LangGraph or otherwise) — orchestration frameworks solve execution-loop problems; this system has a scoring problem

When to revisit

If a future phase decides the system should actually execute a composed chain against real APIs (not just recommend one), that is a different system with a different risk profile — different audit requirements, different error-handling semantics (a 400 from a real API is not the same as a low schema-compatibility score), and likely warrants the execute/evaluate/self-correct pattern with proper guardrails. That is out of scope for the current SRS and should be scoped as its own project if it comes up.

4. API layer: none (direct function calls), not GraphQL

Decision

No GraphQL layer. Streamlit pages call Python functions in core/ directly.

Reasoning

  • This UI has a small, enumerable set of query needs across both use cases: node detail, node neighbors, findings by pattern, merge candidate detail, impact tree, composition candidate detail — a handful of Python functions cover all of them
  • Since the app layer is Streamlit calling Python directly, there's no network boundary to put a query language in front of

When to revisit

  • The UI's query needs become unpredictable or highly varied
  • This data needs to be exposed to many external consumer teams with different shape needs

5. Vector store: pgvector (inside PostgreSQL), not a separate vector DB

Decision

Use the pgvector PostgreSQL extension for all embedding storage and similarity search. This consolidates the entire data layer — relational tables, field rows, field mappings, and vector embeddings — into a single PostgreSQL instance. No separate vector database to operate, secure, back up, or migrate between environments.

Reasoning

Concern Separate vector DB (e.g. ChromaDB, Pinecone) pgvector
Infrastructure Second service to deploy, monitor, back up Already inside PostgreSQL — no extra service
Joins with relational data Requires two queries + application-layer join Native SQL JOIN — e.g. SELECT n.project_name, 1 - (e.embedding <=> q) AS similarity FROM node_embeddings e JOIN api_nodes n ON n.node_id = e.node_id
Transactions Eventual consistency between two systems Full ACID — node + embedding inserted in the same transaction
Scale at this project 9K–12K vectors easily managed Efficient up to millions of vectors with IVFFlat or HNSW index
Filtering before/after similarity Metadata filters in a separate system Direct WHERE clause on JOINed relational columns

The JOIN capability is the decisive factor: composition candidate queries need to combine "find APIs semantically similar to this requirement" with "filter to only active nodes in a specific domain with at least one response field." In pgvector this is one SQL query. In a separate vector DB this is two round-trips plus application code to cross-reference.

6. Schema compatibility: structured field rows, not prose-only

Decision

  • This must be decided now, not retrofitted — if APIs are ingested with prose-only field capture, adding structured fields later means re-extracting from source for every already-ingested API

When to revisit

Not expected to need revisiting — this is a foundational capture decision, not a scale-dependent one.

The 8 supporting tables (source_repos, ingestion_runs, api_versions, domain_taxonomy/functionality_taxonomy, team_directory, api_specs, edge_history, graph_snapshots — see 01-srs.md Section 3.9) are created in Milestone M1, alongside the 10 core tables, even though several stay empty until much later milestones populate them.

Reasoning

  • These tables exist to close specific correctness/traceability gaps that only become visible at real scale (~3,000 nodes from ~2,000+ repos, refreshed on a recurring schedule) — they are not visible problems at sample-data scale, which is exactly why it's easy to skip them and only notice the gap later
  • Adding them after data already exists in the core tables means either a backfill migration or accepting that historical data has no provenance/versioning — both worse than the small upfront cost of creating empty tables now
  • Specific risks each one closes:
  • Without api_versions, the duplicate-flow rule can produce false positives between two versions of the same API
  • Without domain_taxonomy/functionality_taxonomy, free-text variants ("payments" vs "Payments") silently fragment domain-alignment scoring with no visible error
  • Without graph_snapshots, "what changed since last week" has no clean boundary to query against once M11's refresh job is live
  • Without source_repos/api_specs/ingestion_runs, a failed or wrong extraction is invisible until someone notices missing or incorrect data, with no record of why

When to revisit

Not scale-dependent — this is a one-time foundational decision made now specifically because retrofitting it later is expensive, not because it might become necessary later.

9. Internal LLM: four integration points, not a replacement for determinism

Decision

The internal LLM is used at four specific points in the pipeline, each chosen because deterministic logic structurally cannot do the job there. It supplements SQL, vector similarity, and formula scoring — it does not replace them.

The four points and why each is placed there

Point Stage LLM role Why LLM, not deterministic
Query Expansion Before vector retrieval Expand short queries into semantic variants "mandate debit" and "recurring payment collection" are the same concept — SQL and even vector search can miss this without expansion
Field Equivalence Schema compatibility (ambiguous zone only) "Are mandate_id and mandate_ref the same business concept?" SQL fuzzy matching sees string similarity, not semantic equivalence across naming conventions
Composition Decision After formula scoring Final DIRECT_MATCH / COMPOSE / NEW_BUILD verdict Formula cannot see deprecated status, async/sync mismatch, team context — LLM reads these alongside the formula scores
Discovery Quick-Take After SQL results render (async) "Does this API actually satisfy what the developer asked?" Similarity score (0.82) doesn't say "yes" in plain English — LLM provides a human-readable verdict without blocking search results

What the LLM is explicitly NOT used for

  • Graph traversal, flow building, structural redundancy rules
  • Exact field matching (SQL covers ≥0.80 confidence)
  • Taxonomy filtering or domain lookup
  • Audit log writes or status updates

Auditability requirement

Every LLM call writes to llm_call_log (system prompt, user prompt, response, latency) before returning — see 07-llm-integration-guide.md. This is not optional: "why did the system recommend X" must be answerable from logs alone.

When to revisit

  • If the internal LLM endpoint changes URL or auth scheme — update .env only, no code changes (see 07-llm-integration-guide.md Section 2)
  • If query expansion latency becomes unacceptable — add a cache keyed on query text (most developers repeat similar queries)

def detect_search_mode(query: str) -> str:
    if re.match(r'^[a-z][a-z0-9]*(_[a-z0-9]+)+$', query.strip()):
        return 'field'           # snake_case → likely a field name
    if query.strip() in known_domains or query.strip() in known_functionalities:
        return 'taxonomy'        # exact match against taxonomy tables
    return 'semantic'            # everything else

5a.3 SQL — each search mode

Mode 1: Semantic search (most common)

-- :query_vec = embedding of the developer's text
-- Returns APIs ordered by how well their purpose matches the query
SELECT
    n.node_id,
    n.project_name,
    n.layer,
    dt.domain_name                              AS domain,
    ft.functionality_name                        AS functionality,
    n.listener_endpoint,
    n.purpose_text,
    n.owning_team,
    1 - (e.embedding <=> :query_vec::vector)     AS relevance_score
FROM node_embeddings e
JOIN api_nodes n         ON n.node_id = e.node_id
JOIN domain_taxonomy dt  ON dt.domain_id = n.domain_id
JOIN functionality_taxonomy ft ON ft.functionality_id = n.functionality_id
WHERE e.chunk_type = 'purpose'
  AND n.status     = 'active'
  AND 1 - (e.embedding <=> :query_vec::vector) >= 0.50  -- lower threshold than composition (browsing, not deciding)
ORDER BY e.embedding <=> :query_vec::vector
LIMIT 20;

Mode 2: Field name search

-- Developer typed a field name — find APIs that accept or return it
-- Covers both request and response fields
SELECT DISTINCT
    n.node_id,
    n.project_name,
    n.layer,
    dt.domain_name    AS domain,
    f.direction,
    f.field_name,
    f.data_type,
    f.is_required,
    f.description     AS field_description
FROM api_fields f
JOIN api_nodes n         ON n.node_id = f.node_id
JOIN domain_taxonomy dt  ON dt.domain_id = n.domain_id
WHERE n.status = 'active'
  AND (
      f.field_name = :field_name                            -- exact match first
      OR f.field_name ILIKE '%' || :field_name || '%'       -- partial match
  )
ORDER BY
    CASE WHEN f.field_name = :field_name THEN 0 ELSE 1 END, -- exact matches first
    n.project_name;

Mode 3: Taxonomy / domain / functionality search

-- Developer typed a known domain or functionality name
SELECT
    n.node_id,
    n.project_name,
    n.layer,
    dt.domain_name          AS domain,
    ft.functionality_name    AS functionality,
    n.listener_endpoint,
    n.purpose_text,
    n.owning_team
FROM api_nodes n
JOIN domain_taxonomy dt         ON dt.domain_id = n.domain_id
JOIN functionality_taxonomy ft  ON ft.functionality_id = n.functionality_id
WHERE n.status = 'active'
  AND (
      dt.domain_name ILIKE '%' || :query || '%'
      OR ft.functionality_name ILIKE '%' || :query || '%'
  )
ORDER BY n.layer, n.project_name;

Combined — run all three in parallel, merge and deduplicate:

def search_apis(query: str, conn, filters: dict = None) -> list[dict]:
    """
    Unified search entry point for the API Discovery screen.
    Runs all three modes and returns a merged, deduplicated, ranked list.
    """
    mode = detect_search_mode(query)
    results = {}

    if mode == 'semantic':
        vec = get_embedding(query)
        rows = run_semantic_search(vec, conn, filters)
        for r in rows:
            results[r['node_id']] = {**r, 'match_type': 'semantic', 'relevance': r['relevance_score']}

    elif mode == 'field':
        rows = run_field_search(query, conn)
        for r in rows:
            if r['node_id'] not in results:
                results[r['node_id']] = {**r, 'match_type': 'field', 'relevance': 0.90}

    elif mode == 'taxonomy':
        rows = run_taxonomy_search(query, conn)
        for r in rows:
            if r['node_id'] not in results:
                results[r['node_id']] = {**r, 'match_type': 'taxonomy', 'relevance': 0.85}

    # apply layer / domain filters if set
    if filters:
        if filters.get('layer'):
            results = {k: v for k, v in results.items() if v['layer'] == filters['layer']}
        if filters.get('domain'):
            results = {k: v for k, v in results.items() if v['domain'] == filters['domain']}

    return sorted(results.values(), key=lambda x: x['relevance'], reverse=True)

6.0 How RAG and the LLM actually work together here

This screen is a RAG pipeline, not a single LLM call. It's worth being explicit about the order of operations, because each stage exists to narrow what the next stage has to consider — skipping a stage either breaks correctness or makes the LLM call expensive and unreliable.

User types a requirement in plain English
        │
        ▼
┌───────────────────────┐
│ 1. RETRIEVE (Vector DB) │   embed the requirement text, cosine-search
│                         │   node_embeddings WHERE chunk_type='purpose'          │
└───────────────────────┘
        │  top-K candidate APIs (typically K=5), NOT the full ~3,000 node set
        ▼
┌───────────────────────┐
│ 2. VALIDATE (SQL)       │   for any 2+ candidates proposed as a chain, look up
│                         │   precomputed field_mappings (deterministic, no LLM)
└───────────────────────┘
        │  schema_compatibility_score per candidate pair
        ▼
┌───────────────────────┐
│ 3. SCORE (Python)       │   composite_confidence = weighted blend of
│                         │   similarity + schema compatibility + domain alignment
└───────────────────────┘
        │  banded result: DIRECT_MATCH | COMPOSE | NEW_BUILD
        ▼
┌───────────────────────┐
│ 4. EXPLAIN (LLM)        │   ONLY the already-scored, already-validated candidates
│                         │   go to the LLM — it writes the rationale, it does not
│                         │   decide the score
└───────────────────────┘
        │
        ▼
Composition Advisor screen renders the result + rationale
Human approves or rejects

Why this order, specifically:

  • Retrieval narrows the field first. Without Step 1, the LLM would need every API's full documentation in its prompt to even consider what's relevant — at ~3,000 nodes that's far past any practical context window, and even if it fit, the LLM would be doing what a vector search already does cheaply and reliably.
  • Schema validation runs in SQL, not the LLM. Whether field customer_id satisfies field cust_id is a deterministic lookup against precomputed field_mappings (Section 5.2 of 01-srs.md) — asking an LLM to "check if these fields are compatible" by reading prose is slower, less consistent, and harder to audit than a SQL join. The LLM never re-derives this; it only narrates a result that's already computed.
  • The LLM's job is explanation, not decision. By the time a candidate reaches Step 4, its DIRECT_MATCH/COMPOSE/NEW_BUILD band and numeric scores are already final. The LLM call's only output is llm_rationale — human-readable text justifying what the score already determined. This is deliberate: it keeps the recommendation auditable (you can always point to the exact numbers that produced a band) and keeps the LLM call cheap (small, focused prompt per candidate, not a sprawling "figure out everything" prompt).
  • Nothing here executes anything. Per 02-architecture.md Section 3, this pipeline ends at a recommendation. There is no Step 5 that calls a live API — that would be a different system with a different risk profile, intentionally out of scope (see 01-srs.md Section 1.2).

2. Field path notation for nested JSON structures

2.0 Why this matters

Real Mule API payloads are almost always nested JSON — not flat key-value lists. The api_fields table uses field_path (dot-notation) and field_name (leaf only) to represent this structure. Getting this right matters because the composition validator matches on field_name — if two nested fields from different APIs both have the leaf name customer_id, the validator can detect that API A's response can feed API B's request even though one is at data.customer.customer_id and the other is at customer_id at root level.

2.1 Dot-notation rules

Rule Example
Top-level field field_path = "mandate_id"
One level of nesting field_path = "customer.customer_id"
Two levels deep field_path = "customer.address.city"
Array of objects field_path = "items[].sku_id" (use [] to indicate an array element)
Array of objects, deeper field_path = "items[].price.amount"
field_name is always the leaf field_name = "city" for field_path = "customer.address.city"

2.4 What the leaf-name matcher sees

When the composition validator checks "does API A's response satisfy API B's request":

API A response has: items[].price.amount  →  leaf: amount
API B request needs: payment.amount       →  leaf: amount

Result: EXACT leaf match — satisfied
        (the nesting difference doesn't matter for compatibility scoring)

API A response has: customer.contact.mobile  →  leaf: mobile
API B request needs: mobile_number           →  leaf: mobile_number

Result: FUZZY match at ~0.80 (similar but not identical)
        → LLM field-equivalence check triggered (Point 2 in 07-llm-integration-guide.md)

API A response has: debit.amount   →  leaf: amount
API B request needs: claim_amount  →  leaf: claim_amount

Result: FUZZY match at ~0.60 (ambiguous)
        → LLM check: "are these the same concept in domain='claims'?" → NO

For request_fields_structured and response_fields_structured:
- Use dot-notation for nested objects: "customer.address.city"

  "customer.address.city" → field_name = "city"
- For each field include: path, type (string/integer/decimal/boolean/date/datetime/object/array),

  with type=object — only add rows for the actual leaf fields inside it)

    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

When to build the index: build after bulk insert, not before. Every row inserted into an HNSW index during construction is slower than batch. The pattern is: load all rows with the index absent or IVFFlat (cheap incremental inserts), then CREATE INDEX once (or REINDEX after a large update batch). For the sample dataset, this doesn't matter — for 3,000+ nodes it does.

4.1 Step 1 — Insert node, get back its node_id

import psycopg2
from psycopg2.extras import RealDictCursor
import json

DB_URL = "postgresql://user:password@localhost:5432/api_graph"

def insert_node(api_doc: dict, conn) -> int:
    """Insert one API into api_nodes and return the assigned node_id."""
    sql = """
        INSERT INTO api_nodes
            (project_name, layer, listener_endpoint, functionality,
             domain, purpose_text, owning_team, status)
        VALUES (%s, %s, %s, %s, %s, %s, %s, 'active')
        ON CONFLICT (project_name) DO UPDATE
            SET listener_endpoint = EXCLUDED.listener_endpoint,
                functionality     = EXCLUDED.functionality,
                domain            = EXCLUDED.domain,
                purpose_text      = EXCLUDED.purpose_text,
                owning_team       = EXCLUDED.owning_team
        RETURNING node_id
    """
    purpose_text = f"{api_doc.get('overview', '')} {api_doc.get('business_purpose', '')}".strip()

    with conn.cursor() as cur:
        cur.execute(sql, (
            api_doc['project_name'], api_doc['layer'],
            api_doc.get('listener_endpoint'), api_doc.get('functionality'),
            api_doc.get('domain'), purpose_text, api_doc.get('owning_team')
        ))
        node_id = cur.fetchone()[0]
    conn.commit()

    api_doc['node_id'] = node_id  # write back so downstream steps have it
    return node_id

4.2 Step 2 — Insert edges (resolve project names to node_ids)

def insert_edges(edge_docs: list[dict], conn):
    """
    Insert all edges. Resolves project_name -> node_id.
    Skips edges where either project is not yet in api_nodes (logs a warning).
    """
    with conn.cursor(cursor_factory=RealDictCursor) as cur:
        cur.execute("SELECT node_id, project_name FROM api_nodes")
        name_to_id = {r['project_name']: r['node_id'] for r in cur.fetchall()}

    rows_ok, rows_skipped = [], []
    for e in edge_docs:
        src = name_to_id.get(e['source_project_name'])
        tgt = name_to_id.get(e['target_project_name'])
        if not src or not tgt:
            rows_skipped.append(e)
            continue
        rows_ok.append((
            src, tgt,
            e['source_project_name'], e['target_project_name'],
            e.get('source_endpoint_path'), e.get('target_endpoint_path'),
            e.get('call_type', 'sync')
        ))

    if rows_ok:
        with conn.cursor() as cur:
            from psycopg2.extras import execute_values
            execute_values(cur, """
                INSERT INTO api_edges
                    (source_node_id, target_node_id,
                     source_project_name, target_project_name,
                     source_endpoint_path, target_endpoint_path, call_type)
                VALUES %s
                ON CONFLICT (source_node_id, target_node_id,
                             source_endpoint_path, target_endpoint_path)
                DO NOTHING
            """, rows_ok)
        conn.commit()

    if rows_skipped:
        print(f"WARNING: {len(rows_skipped)} edges skipped — project not found:")
        for e in rows_skipped:
            print(f"  {e['source_project_name']} → {e['target_project_name']}")

    return len(rows_ok), len(rows_skipped)

from psycopg2.extras import execute_values

def insert_structured_fields(api_doc: dict, conn):
    """
    Insert request and response fields as per-field rows into api_fields.
    This is the data that powers field_mappings and the composition validator.
    """
    node_id = api_doc['node_id']
    rows = []

    for direction in ['request', 'response']:
        for field in api_doc.get(f'{direction}_fields_structured', []):
            rows.append((
                node_id,
                direction,
                field['path'],
                field['path'].split('.')[-1],   # leaf field name
                field.get('type'),
                field.get('required', False),
                field.get('description'),
                field.get('example')
            ))

    if not rows:
        print(f"WARNING: no structured fields for node {node_id} "
              f"({api_doc['project_name']}) — composition validator will be blind for this API")
        return

    with conn.cursor() as cur:
        execute_values(cur, """
            INSERT INTO api_fields
                (node_id, direction, field_path, field_name,
                 data_type, is_required, description, sample_value)
            VALUES %s
            ON CONFLICT DO NOTHING
        """, rows)
    conn.commit()
    print(f"  {api_doc['project_name']}: {len(rows)} field rows inserted")

import numpy as np
from psycopg2.extras import execute_values

def get_embedding(text: str) -> list[float]:
    """
    Call your internal LLM embedding endpoint.
    Must return a list of floats matching your VECTOR() column dimension.

    Example (OpenAI-compatible):
        import requests
        r = requests.post(
            "https://your-internal-llm/v1/embeddings",
            headers={"Authorization": f"Bearer {API_KEY}"},
            json={"input": text, "model": "text-embedding-3-small"}
        )
        return r.json()["data"][0]["embedding"]
    """
    raise NotImplementedError("Wire up your embedding endpoint here")


def build_embed_chunks(api_doc: dict) -> list[dict]:
    """
    Build the 3–4 prose chunks per API that get embedded.
    Returns list of {chunk_type, text} dicts.
    """
    chunks = [{
        'chunk_type': 'purpose',
        'text': f"{api_doc.get('overview', '')} {api_doc.get('business_purpose', '')}".strip()
    }]
    if api_doc.get('business_rules'):
        chunks.append({'chunk_type': 'business_rules', 'text': api_doc['business_rules']})
    if api_doc.get('request_fields_prose'):
        chunks.append({'chunk_type': 'request_fields', 'text': api_doc['request_fields_prose']})
    if api_doc.get('response_fields_prose'):
        chunks.append({'chunk_type': 'response_fields', 'text': api_doc['response_fields_prose']})
    return chunks


def insert_embeddings(api_doc: dict, conn):
    """Embed each chunk and upsert into node_embeddings."""
    node_id = api_doc['node_id']
    chunks  = build_embed_chunks(api_doc)
    rows    = []

    for c in chunks:
        if not c['text'].strip():
            continue
        vector = get_embedding(c['text'])    # your internal LLM call
        rows.append((node_id, c['chunk_type'], c['text'], vector))

    if not rows:
        return

    with conn.cursor() as cur:
        execute_values(cur, """
            INSERT INTO node_embeddings (node_id, chunk_type, embed_text, embedding)
            VALUES %s
            ON CONFLICT (node_id, chunk_type) DO UPDATE
                SET embed_text = EXCLUDED.embed_text,
                    embedding  = EXCLUDED.embedding,
                    updated_at = NOW()
        """, rows, template="(%s, %s, %s, %s::vector)")
    conn.commit()
    print(f"  {api_doc['project_name']}: {len(rows)} embeddings upserted")

4.6 Full pipeline — orchestrator

import psycopg2

def run_full_ingestion(api_docs: list[dict], edge_docs: list[dict]):
    """
    Full ingestion pass for all APIs and edges.
    api_docs: list of per-API JSON documents (Section 2.1)
    edge_docs: list of per-edge JSON documents (Section 2.2)
    """
    conn  = psycopg2.connect(DB_URL)
    stats = {'scanned': 0, 'succeeded': 0, 'failed': 0,
             'nodes_created': 0, 'edges_created': 0, 'nodes_updated': 0}

    run_id = start_ingestion_run('full_scan', conn)
    print(f"Ingestion run {run_id} started")

    # ── Step 1: nodes ──────────────────────────────────────────────────
    for api_doc in api_docs:
        stats['scanned'] += 1
        try:
            node_id = insert_node(api_doc, conn)
            stats['nodes_created'] += 1
            print(f"[{stats['scanned']}/{len(api_docs)}] Node {node_id}: {api_doc['project_name']}")

            # ── Step 3: structured fields ──────────────────────────────
            insert_structured_fields(api_doc, conn)

            # ── Step 4: embeddings ─────────────────────────────────────
            insert_embeddings(api_doc, conn)

            # ── Step 5: provenance ─────────────────────────────────────
            repo_id = insert_source_repo(api_doc, run_id, conn)
            insert_api_spec(api_doc, repo_id, run_id, conn)

            stats['succeeded'] += 1

        except Exception as e:
            stats['failed'] += 1
            print(f"ERROR processing {api_doc.get('project_name', '?')}: {e}")
            conn.rollback()

    # ── Step 2: edges (after all nodes are inserted) ───────────────────
    ok, skipped = insert_edges(edge_docs, conn)
    stats['edges_created'] = ok
    print(f"Edges: {ok} inserted, {skipped} skipped")

    finish_ingestion_run(run_id, stats, conn)
    conn.close()

    print(f"\nIngestion run {run_id} complete:")
    print(f"  Nodes:  {stats['succeeded']} succeeded, {stats['failed']} failed")
    print(f"  Edges:  {stats['edges_created']} inserted")

def find_similar_nodes(query_text: str, conn, chunk_type='purpose',
                       top_k=5, threshold=0.75) -> list[dict]:

    query_vector = get_embedding(query_text)

            n.node_id,

            n.layer,
            n.domain,

import re

def detect_search_mode(query: str) -> str:
    """
    Auto-detect which search mode to use based on query shape:
    - snake_case pattern     → 'field'    (e.g. mandate_id, customer_ref_no)
    - known domain/function  → 'taxonomy' (e.g. payments, NACH Debit)
    - everything else        → 'semantic' (plain English requirement)

    q = query.strip()
    if re.match(r'^[a-z][a-z0-9]*(_[a-z0-9]+)+$', q):
        return 'field'
    # taxonomy check happens in search_apis() after DB lookup
    return 'semantic'

9.5 search_all_variants() — unified search across expanded queries

Referenced in 07-llm-integration-guide.md Section 7 (Discovery screen Streamlit code). Combines query expansion (LLM Point 1) with all three search modes, then deduplicates results ranked by best relevance score across all variants.

def search_all_variants(variants: list[str], conn,
                        filters: dict = None) -> list[dict]:
    """
    Run semantic search for each query variant (original + LLM expansions),
    union the results, deduplicate by node_id keeping the highest relevance score.

    variants: output of llm.expand_query() — [original, variant1, variant2, ...]
    filters:  optional {layer, domain} dict from filter pills in the UI
    """
    seen: dict[int, dict] = {}   # node_id → best result so far

    for variant in variants:
        vec  = get_embedding(variant)    # core/llm.get_embedding()
        rows = run_semantic_search(vec, conn, filters)

        for r in rows:
            nid = r['node_id']
            # Keep the highest relevance score across all query variants
            if nid not in seen or r['relevance_score'] > seen[nid]['relevance']:
                seen[nid] = {**r, 'relevance': r['relevance_score']}

    # Also run field/taxonomy search on the ORIGINAL query only
    original = variants[0]
    mode = detect_search_mode(original)

    if mode == 'field':
        for r in run_field_search(original, conn):
            nid = r['node_id']
            if nid not in seen:
                seen[nid] = {**r, 'relevance': 0.90, 'match_type': 'field'}

    elif mode == 'taxonomy':
        for r in run_taxonomy_search(original, conn):
            nid = r['node_id']
            if nid not in seen:
                seen[nid] = {**r, 'relevance': 0.85, 'match_type': 'taxonomy'}

    # Apply filters if any
    results = list(seen.values())
    if filters:
        if filters.get('layer'):
            results = [r for r in results if r.get('layer') == filters['layer']]
        if filters.get('domain'):
            results = [r for r in results if r.get('domain') == filters['domain']]

    return sorted(results, key=lambda x: x['relevance'], reverse=True)

LLM Integration Guide

Internal LLM — Where, How, and Why

Purpose: Defines exactly where the internal LLM is used in the pipeline, what it decides vs. what deterministic logic decides, how to configure the endpoint, and the exact prompts for each usage point.

This is the authoritative guide for core/llm.py.

1. Design principle: LLM supplements determinism, never replaces it

The internal LLM is expensive (latency + cost) and non-deterministic (same input can produce different output on different runs). Every LLM call in this system is placed at a point where:

  1. Deterministic logic has already done what it can — SQL, vector similarity, and field-mapping checks run first
  2. The LLM adds something deterministic logic structurally cannot — contextual reasoning, semantic field-name equivalence, requirement interpretation
  3. The output is auditable — every LLM call's input and output is logged to llm_call_log (Section 2.3) so decisions can be explained later

The formula (composition_confidence = 0.40×similarity + 0.35×schema + 0.25×domain) is not replaced by the LLM — it becomes an input signal the LLM reads, alongside the raw purpose text, field information, and the requirement. The LLM makes the final band decision informed by the formula, not blind to it.

MAX_RETRIES   = int(os.getenv("INTERNAL_LLM_MAX_RETRIES", 2))


def call_llm(system_prompt: str, user_prompt: str,
             temperature: float = 0.1, max_tokens: int = 500) -> str:
    """
    Single entry point for all LLM calls.
    Returns the content string from the first choice.
    Raises on non-200 after MAX_RETRIES attempts.
    """
    headers = {
        "Authorization": f"Bearer {LLM_API_KEY}",
        "Content-Type": "application/json"
    }
    body = {
        "model": LLM_MODEL,
        "temperature": temperature,     # low temp for structured decisions
        "max_tokens": max_tokens,
        "messages": [
            {"role": "system", "content": system_prompt},
            {"role": "user",   "content": user_prompt}
        ]
    }

    for attempt in range(1, MAX_RETRIES + 1):
        try:
            resp = requests.post(LLM_URL, headers=headers,
                                 json=body, timeout=TIMEOUT)
            resp.raise_for_status()
            return resp.json()["choices"][0]["message"]["content"]
        except Exception as e:
            log.warning(f"LLM call attempt {attempt} failed: {e}")
            if attempt == MAX_RETRIES:
                raise
            time.sleep(2 ** attempt)


def get_embedding(text: str) -> list[float]:
    """
    Get a vector embedding from the internal LLM embedding endpoint.
    Returns a list of floats matching the VECTOR() dimension in node_embeddings.
    """
    headers = {
        "Authorization": f"Bearer {LLM_API_KEY}",
        "Content-Type": "application/json"
    }
    body = {"model": EMBED_MODEL, "input": text}
    resp = requests.post(EMBED_URL, headers=headers, json=body, timeout=TIMEOUT)
    resp.raise_for_status()
    return resp.json()["data"][0]["embedding"]

4. LLM Point 1 — Query Expansion

Where: core/search.py — called before vector retrieval in both API Discovery and Composition Advisor.

Why: Short or domain-specific queries ("mandate debit") may miss semantically equivalent APIs described with different terminology ("standing instruction", "auto-debit", "recurring collection"). The LLM expands the query into variants, all are embedded and searched, results are union-merged and deduplicated.

When to skip: if the query is already long (>10 words) or contains known domain/functionality terms (detected by taxonomy match), expansion adds little — skip the LLM call and embed the original directly.

Prompt

QUERY_EXPANSION_SYSTEM = """You are an API catalogue search assistant.
Your job is to expand a developer's search query into alternative phrasings
that might match how an API's purpose is described in documentation.

Return ONLY a JSON array of 3 alternative query strings.
Do not include the original query.
Do not add explanations.
Keep each alternative under 15 words.
Focus on: synonyms, related technical terms, and alternative business descriptions.

Example input: "mandate debit"
Example output: ["recurring direct debit collection", "auto-debit standing instruction processing", "scheduled payment mandate execution"]
"""

def expand_query(query: str) -> list[str]:
    """
    Expand a short query into 3 semantic variants.
    Returns original query + variants for union search.
    Skips expansion if query is long or matches taxonomy.
    """
    if len(query.split()) > 10:
        return [query]   # already descriptive, no expansion needed

    try:
        raw = call_llm(
            system_prompt=QUERY_EXPANSION_SYSTEM,
            user_prompt=f"Expand this search query: {query}",
            temperature=0.3,    # slightly higher — we want creative variants
            max_tokens=150
        )
        variants = json.loads(raw)
        log_llm_call('query_expansion', None, QUERY_EXPANSION_SYSTEM,
                     query, raw)
        return [query] + variants[:3]   # original first, then up to 3 variants
    except Exception as e:
        log.warning(f"Query expansion failed, using original: {e}")
        return [query]   # graceful fallback — search still works

5. LLM Point 2 — Field Equivalence (supplement only)

Where: core/composition.py — called only for field pairs where fuzzy match confidence is between 0.50 and 0.79 (the ambiguous zone). Exact matches (1.0) and clearly non-matching pairs (<0.50) never touch the LLM.

Why: Different teams use different naming conventions for the same concept — customer_id, cust_id, customerIdentifier, custRef. SQL fuzzy matching catches partial string overlap but cannot reason about semantic equivalence. The LLM can.

When to skip: confidence ≥ 0.80 (SQL already confident) or < 0.50 (clearly different — LLM won't help).

Prompt

FIELD_EQUIV_SYSTEM = """You are an API schema analyst.
Determine whether two field names from different APIs refer to the same
business concept, given the domain context.

Return ONLY valid JSON in this exact format:
{
  "equivalent": true | false,
  "confidence": 0.0 to 1.0,
  "reason": "one sentence explanation"
}

"""

def check_field_equivalence(field_a: str, type_a: str,
                             field_b: str, type_b: str,
                             domain: str) -> dict:
    """
    Ask the LLM whether two field names are semantically equivalent.
    Only called when SQL fuzzy confidence is 0.50-0.79.
    Returns {equivalent, confidence, reason}.
    """
    user_prompt = f"""Domain: {domain}

Field A: '{field_a}' (type: {type_a})
Field B: '{field_b}' (type: {type_b})

Are these the same business concept?"""

    try:
        raw = call_llm(FIELD_EQUIV_SYSTEM, user_prompt,
                       temperature=0.0, max_tokens=100)
        result = json.loads(raw)
        log_llm_call('field_equivalence', None, FIELD_EQUIV_SYSTEM,
                     user_prompt, raw)
        return result
    except Exception:
        return {"equivalent": False, "confidence": 0.0,
                "reason": "LLM check failed — treating as non-equivalent"}


def compute_field_mappings_with_llm(source_node_id: int,
                                     target_node_id: int,
                                     domain: str, conn) -> list[dict]:
    """
    Enhanced version of the original compute_field_mappings().
    SQL fuzzy is primary; LLM resolves the ambiguous zone only.
    """
    source_fields = get_fields(conn, source_node_id, direction='response')
    target_fields = get_fields(conn, target_node_id, direction='request')

    mappings = []
    for tf in target_fields:
        best_match, best_score = None, 0.0

        for sf in source_fields:
            if sf['field_name'] == tf['field_name']:
                score, match_type = 1.0, 'exact_name'
            elif fuzzy_score(sf['field_name'], tf['field_name']) >= 0.80:
                score, match_type = 0.80, 'fuzzy_name'
            elif fuzzy_score(sf['field_name'], tf['field_name']) >= 0.50:
                # Ambiguous zone — ask LLM
                equiv = check_field_equivalence(
                    sf['field_name'], sf['data_type'],
                    tf['field_name'], tf['data_type'],
                    domain
                )
                score = equiv['confidence'] if equiv['equivalent'] else 0.0
                match_type = 'llm_semantic'
            else:
                continue

            type_ok = types_compatible(sf['data_type'], tf['data_type'])
            if not type_ok:
                score *= 0.5

            if score > best_score:
                best_score = score
                best_match = {
                    'source_field': sf,
                    'match_type': match_type,
                    'confidence': score,
                    'type_compatible': type_ok
                }

        mappings.append({
            'target_field': tf,
            'match': best_match,
            'satisfied': best_match is not None and best_match['confidence'] >= 0.70,
            'required_but_unsatisfied': (
                tf['is_required'] and
                (best_match is None or best_match['confidence'] < 0.70)
            )
        })

    return mappings

6. LLM Point 3 — Composition Decision (primary)

Where: core/composition.py — after the formula produces numeric scores, the LLM reads those scores alongside the full API context and makes the final DIRECT_MATCH / COMPOSE / NEW_BUILD call.

Why the formula alone is insufficient: - Formula cannot see that an API is deprecated (status field exists but the formula doesn't weight it) - Formula cannot detect call_type mismatch (requirement says async, API is sync-only) - Formula cannot reason about team/ownership context - Formula treats similarity as a pure number — LLM can see "this API does something adjacent but not the same"

The formula's output becomes an input to the LLM prompt, not a replacement. This keeps the decision auditable (formula scores are always shown alongside the LLM's verdict).

Prompt

COMPOSITION_DECISION_SYSTEM = """You are an API architecture advisor for a
Mule integration platform. Your job is to decide whether existing APIs satisfy
a developer's new requirement, based on evidence provided.

You will receive:
- The new requirement
- Top candidate APIs retrieved by semantic similarity
- For multi-API chains: field compatibility analysis
- Pre-computed numeric scores (as signals, not verdicts)

Return ONLY valid JSON in this exact format:
{
  "recommendation": "DIRECT_MATCH" | "COMPOSE" | "NEW_BUILD",
  "confidence": "HIGH" | "MEDIUM" | "LOW",
  "target_apis": ["api-name-1", "api-name-2"],
  "rationale": "2-3 sentences explaining your decision",
  "risks": "1 sentence on main risk or concern, or null if none",
  "disqualifiers": ["list any APIs from candidates that should NOT be used, with one-word reason each"]
}

Decision guide:
  DIRECT_MATCH: One API clearly satisfies the full requirement. Similarity >= 0.75,
                schema shows required fields present, no disqualifying factors.
  COMPOSE:      No single API satisfies the full requirement, but 2-3 existing APIs
                chained together would. Field compatibility must be adequate (no
                required fields permanently unresolvable).
  NEW_BUILD:    No existing API comes close, or all candidates have disqualifying
                factors (deprecated, wrong call_type, wrong layer for this use case).

Be conservative: prefer COMPOSE over NEW_BUILD if there's a reasonable chain.
Prefer NEW_BUILD over DIRECT_MATCH if there's meaningful doubt.
"""

def make_composition_decision(requirement: str,
                               candidates: list[dict],
                               field_mappings: list[dict],
                               formula_scores: dict) -> dict:
    """
    LLM-primary composition decision.
    candidates: list of retrieved APIs with purpose, layer, domain, status, call_type
    field_mappings: output of compute_field_mappings_with_llm()
    formula_scores: {similarity, schema_compat, domain_alignment, composite}
    """
    # Build the candidate summary for the prompt
    candidate_summary = []
    for c in candidates:
        candidate_summary.append({
            "api_name":      c['project_name'],
            "layer":         c['layer'],
            "domain":        c['domain'],
            "functionality": c.get('functionality'),
            "purpose":       c['purpose_text'],
            "status":        c['status'],          # active/deprecated — LLM sees this
            "call_type":     c.get('call_type', 'sync'),
            "similarity":    round(c['similarity_score'], 3)
        })

    # Build field mapping summary if available
    mapping_summary = []
    if field_mappings:
        for m in field_mappings:
            mapping_summary.append({
                "target_field":   m['target_field']['field_name'],
                "required":       m['target_field']['is_required'],
                "satisfied":      m['satisfied'],
                "match_type":     m['match']['match_type'] if m['match'] else None,
                "confidence":     round(m['match']['confidence'], 2) if m['match'] else 0
            })

    user_prompt = f"""New requirement:
"{requirement}"

Candidate APIs (retrieved by semantic similarity):
{json.dumps(candidate_summary, indent=2)}

Field compatibility analysis (for multi-API composition):
{json.dumps(mapping_summary, indent=2) if mapping_summary else "Not applicable — single-API evaluation only"}

Pre-computed numeric signals (for reference):
- Semantic similarity score: {formula_scores.get('similarity', 'N/A')}
- Schema compatibility score: {formula_scores.get('schema_compat', 'N/A')}
- Domain alignment score: {formula_scores.get('domain_alignment', 'N/A')}

Make your recommendation."""

    raw = call_llm(COMPOSITION_DECISION_SYSTEM, user_prompt,
                   temperature=0.1, max_tokens=400)

                 COMPOSITION_DECISION_SYSTEM, user_prompt, raw)
    return result

7. LLM Point 4 — API Discovery Quick-Take (async, secondary reviewer)

Where: app/2_API_Discovery.py — after SQL search results render, the LLM annotates each result card asynchronously. Results show instantly; LLM badges appear 2-3 seconds later.

Why: Search results tell the developer what's available. The LLM quick-take tells them whether it's actually relevant to what they typed. Relevance score alone (0.82) doesn't say "yes this does what you want" in plain English. The LLM can.

Why async (not blocking): A developer's search result appearing in <1 second is a better experience than waiting 3 seconds for LLM annotations. Show results first, overlay annotations after.

Prompt

DISCOVERY_REVIEW_SYSTEM = """You are a quick API relevance checker.
Given a developer's search query and one API's description,
give a one-line verdict on whether this API satisfies the query.

Return ONLY valid JSON:
{
  "verdict": "YES" | "PARTIAL" | "NO",
  "note": "one sentence, max 15 words, plain English, no jargon"
}

YES:     This API clearly does what was asked.
PARTIAL: This API does part of what was asked, or is related but not complete.
NO:      This API does not satisfy the requirement despite the semantic similarity.
"""

def quick_take_single(query: str, api: dict) -> dict:
    """
    One LLM call per API card in Discovery results.
    Returns {verdict: YES|PARTIAL|NO, note: str}.
    """
    user_prompt = f"""Developer query: "{query}"

API: {api['project_name']}
Purpose: {api['purpose_text']}
Domain: {api['domain']}
Functionality: {api.get('functionality', 'N/A')}"""

    try:
        raw = call_llm(DISCOVERY_REVIEW_SYSTEM, user_prompt,
                       temperature=0.0, max_tokens=80)
        result = json.loads(raw)
        log_llm_call('discovery_review', api['node_id'],
                     DISCOVERY_REVIEW_SYSTEM, user_prompt, raw)
        return result
    except Exception:
        return {"verdict": "PARTIAL", "note": "Could not evaluate — review manually"}


def quick_take_batch(query: str, apis: list[dict]) -> list[dict]:
    """
    Run quick_take_single for each API in parallel using ThreadPoolExecutor.
    Returns list of {node_id, verdict, note}, matching input order.
    """
    from concurrent.futures import ThreadPoolExecutor, as_completed
    results = [None] * len(apis)

    with ThreadPoolExecutor(max_workers=5) as executor:
        futures = {
            executor.submit(quick_take_single, query, api): i
            for i, api in enumerate(apis)
        }
        for future in as_completed(futures):
            idx = futures[future]
            results[idx] = {
                "node_id": apis[idx]['node_id'],
                **future.result()
            }

    return results

1. Query Expansion core/search.py Expand short queries into semantic variants before vector retrieval Primary (no deterministic alternative) Yes — but fast (~0.5s), worth it
2. Field Equivalence core/composition.py Resolve ambiguous field name matches (0.50–0.79 confidence zone) Secondary — SQL is primary, LLM supplements ambiguous cases only Yes — called per ambiguous pair, batched where possible

def log_llm_call(call_type: str, entity_id, system_prompt: str,
                  user_prompt: str, response: str, conn=None):
    """Write every LLM call to llm_call_log for auditability."""
    if conn is None:

    with conn.cursor() as cur:
        cur.execute("""
            INSERT INTO llm_call_log
                (call_type, entity_id, system_prompt, user_prompt, llm_response, called_at)
            VALUES (%s, %s, %s, %s, %s, NOW())
        """, (call_type, entity_id, system_prompt, user_prompt, response))
    conn.commit()
