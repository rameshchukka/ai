User Guide

This guide explains how to use the Mule API Structural Detection Platform as an architect, tech lead, or developer. Three screens, each with a specific job.

Who uses which screen

RoleGo toPrimary task
DeveloperFindings DashboardCheck what redundancy exists before starting new work
ArchitectAll three screensReview findings, approve merges, assess impact
Tech LeadGraph Explorer + ImpactUnderstand the call graph, assess change risk

Quick start

1

Open the platform

Navigate to the Streamlit URL your team has configured (e.g. http://api-governance.internal:8501). The Graph Explorer loads as the default screen.

2

Start with the Findings Dashboard

The Findings Dashboard shows all structural anomalies detected in the last refresh. HIGH severity findings (red) are duplicate flows — the most actionable starting point.

3

Navigate between screens

Use the left sidebar. "View in graph" buttons on finding cards open the Graph Explorer with that node pre-selected. "View findings" on a graph node opens the Findings Dashboard filtered to that node.

The governance workflow

Finding detected (weekly refresh)
    |
    v
Findings Dashboard: architect reviews
    |-- Dismiss: false positive, comment explains why
    |-- Mark reviewed: genuine finding
         |
         v (for DUPLICATE_FLOW findings)
    Merge Candidates: architect reviews proposal
         |-- Approve: owning team notified to carry out merge
         |-- Reject: comment explains why these should stay separate
         |-- Defer: re-appears next week

Nothing in this platform changes any API. Approve means "this merge is governance-approved." The actual code change is done by the owning team outside the platform.

Screen 1 — Graph Explorer

The full Mule API call graph visualised as a directed graph. Use this to understand the overall architecture and see where structural anomalies are located.

Reading the graph

What you seeWhat it means

Orange nodeProcess layer (Proc) — orchestration and business logic

Large nodeHigh in-degree — many APIs call this one. A very large Sys node is a shared asset with fan-in risk.

Step by step — exploring a domain

1

Filter to one domain

Use the Domain dropdown in the left sidebar. Select "payments" to see only the payments domain APIs. The graph redraws showing only those nodes and their connections.

2

Enable finding overlay

Check "Show findings overlay". Nodes and edges involved in open findings turn red. This is the fastest way to see where the structural issues are in a domain.

3

Click a node to inspect it

Click any node. The right panel shows: project name, layer, domain, owning team, listener endpoint, and a count of open findings. If the node has findings, a "View findings" button appears.

4

Follow the path

Click an Exp node to see where it leads. Follow the edges through Proc to Sys. If two different Exp nodes both reach the same Sys node, that is a DUPLICATE_FLOW.

Screen 2 — Findings Dashboard

All structural findings from the last graph refresh, sorted by severity. This is where architects review and action findings.

The four finding types

TypeSeverityWhat it meansTypical action
DUPLICATE_FLOWHIGHTwo Exp APIs both reach the same Sys API through different Proc chains. One chain is likely redundant.Review the two chains. If one is genuinely redundant, approve the merge candidate in Screen 3.
PASS_THROUGH_HOPMEDIUMA Proc API calls exactly one downstream API with no orchestration logic. The Exp caller could call the Sys API directly.Verify with the owning team — does this Proc add any transformation? If not, it may be retirable.
DEEP_CHAINLOWA call flow has 4 or more hops. May indicate unnecessary intermediate steps.Review the full chain. Dismiss if the hops are genuinely necessary (e.g. each Proc adds real orchestration).
FAN_IN_CLUSTERLOWA Sys API is called by 3+ different Proc APIs. May be healthy shared reuse or accidental convergence.Review in Impact Analysis. If it is a shared Sys asset, consider formal SLA documentation. If it is accidental duplication, flag for merge review.

Step by step — reviewing a finding

1

Read the finding card

Each card shows the pattern type, severity badge, date detected, and the specific API names and paths involved. For DUPLICATE_FLOW, you see both paths — which Exp goes through which Proc to reach the shared Sys.

2

Open in graph (optional)

Click "View in graph" to open the Graph Explorer with the involved nodes highlighted. Useful for understanding the broader context of a finding.

3

Make a decision

There are two actions available on open findings:

  • Mark reviewed — genuine finding, acknowledged and recorded
  • Dismiss — false positive or intentional design, not a real issue

A comment is mandatory for both. The comment is stored in the audit log and is the governance evidence that this finding was considered.

4

Use the diff filter

After a weekly refresh, the "Diff status" filter lets you see only "new" findings (appeared this week) versus "persisting" (still unresolved from a previous week). Focus your review on new findings first.

What to write in the comment

DecisionGood comment examples
Mark reviewed (DUPLICATE_FLOW)"Both chains confirmed redundant — exp-account-summary chain scheduled for retirement Q2"
"Raised merge candidate — owning team notified"
Dismiss (DUPLICATE_FLOW)"These serve different consumer audiences — exp-customer-360 for CRM, exp-account-summary for mobile app. Intentional separation."
Dismiss (PASS_THROUGH_HOP)"proc-order-status adds request transformation and auth token injection — not a true pass-through."
Dismiss (FAN_IN_CLUSTER)"sys-crm is a shared platform service — multiple callers are expected and healthy. Documenting as intentional."

Filtering tip: Set Pattern to DUPLICATE_FLOW and Status to open. These are the highest-value findings and the most actionable. Process all HIGH severity before moving to MEDIUM and LOW.

Screen 3 — Merge Candidates & Impact Analysis

Two panels in one screen. Left panel: merge proposals generated from DUPLICATE_FLOW findings. Right panel: impact analysis for any API you search.

Left panel — Merge Candidates

A merge candidate is created automatically when a DUPLICATE_FLOW finding is confirmed. It shows which two Proc API chains are candidates for consolidation.

Reading the merge candidate card

FieldWhat it meansWhat to look for
API A ↔ API BThe two Proc APIs that are candidates to mergeAre these genuinely doing the same job?
Structural scoreGraph-shape confidence (0-1). Higher = stronger structural case.> 0.80 = strong structural evidence
Domain alignmentWhether both APIs are in the same domainSame domain = merge is lower risk
Traffic riskLOW / MEDIUM / HIGH based on daily hit countsHIGH risk = staged rollout needed before retiring one API
LLM rationaleAI-generated explanation (Phase 2). "Pending" in Phase 1.In Phase 1: use your own knowledge of the APIs

Making a decision

ActionWhen to useWhat happens
ApproveThe merge is valid and should proceedStatus → 'approved'. Owning team should be notified separately to carry out the actual code change.
RejectDespite the structural finding, these APIs should remain separateStatus → 'rejected'. Finding stays open but candidate is closed.
DeferNeed more information or it is the wrong timeStatus → 'deferred'. Re-appears next week in the candidate list.

Approving a merge candidate is a governance decision, not a technical change. The platform does not modify, retire, or redirect any API. The owning team carries out the actual merge based on the approved governance record.

Right panel — Impact Analysis

Type any project name into the search box to see the full upstream and downstream dependency tree.

Step by step

1

Search for an API

Type a full or partial project name (e.g. "nach-debit" or "proc-nach"). The first matching active API is shown.

2

Read the upstream tree

Upstream = APIs that call this one. Shown with their layer badge, project name, and the exact endpoint path they use to call this API. If empty: "None — this is an entry point" (it is an Exp node with no callers).

3

Read the downstream tree

Downstream = APIs this one calls. Same format. If empty: "None — this is a terminal node" (it is a Sys node that calls no further Mule APIs).

4

Use before any change

Before retiring, modifying, or renaming an API: search for it in Impact Analysis. The upstream list tells you exactly which teams and APIs will be affected by your change.

Common questions

QuestionAnswer
I retired an API — when does it disappear from the graph?On the next weekly refresh, the ingestion job will detect it as missing and mark its edges as 'disappeared' in edge_history. The node status is set to 'retired' and it disappears from all active queries.
Why does my search return no results?The search uses ILIKE %name% — try a shorter fragment. Also check the API is in the DB: SELECT project_name FROM api_nodes WHERE project_name ILIKE '%search%'.
The impact tree looks incomplete — I know there are more callersThe upstream tree shows only edges in api_edges. If a caller is missing, it was not included in the Bitbucket extraction or its calls[] array was empty. Check the source data.
