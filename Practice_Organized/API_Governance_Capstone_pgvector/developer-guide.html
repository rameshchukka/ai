M1b — Taxonomy Seeding & Version Detection

Goal: domain_taxonomy populated with canonical names. Every api_nodes.domain_id set — zero nulls. Version pairs (v1/v2) linked in api_versions so M2's duplicate-flow rule can suppress false positives between versioned APIs.

Why M1b must run before M2: The duplicate-flow rule checks api_versions before raising a finding. If proc-payment-api-v1 and proc-payment-api-v2 both reach the same Sys API, they should NOT be flagged as a duplicate — they are just versioned. Without M1b, every version pair becomes a false positive.

M2 — Traversal & Structural Detection

Goal: The flows table is populated with all materialised call paths. All four structural patterns are detected and written to structural_findings. Duplicate-flow pairs also create merge_candidates rows with a structural score.

How the traversal works

A recursive CTE starts at every active Exp node and follows api_edges forward, building up node_path[] arrays until it reaches a Sys terminal or hits the depth limit (6 hops). Each complete path is one row in flows.

WITH RECURSIVE traverse AS (
  -- Base: every active Exp node
  SELECT node_id AS root_exp_id, node_id AS current_node,
         ARRAY[node_id] AS node_path, 1 AS hop_count, layer
  FROM api_nodes WHERE layer='exp' AND status='active'

  UNION ALL

  -- Follow each outbound edge
  SELECT t.root_exp_id, e.target_node_id,
         t.node_path || e.target_node_id,
         t.hop_count + 1,
         n.layer
  FROM traverse t
  JOIN api_edges e ON e.source_node_id = t.current_node
  JOIN api_nodes n ON n.node_id = e.target_node_id
  WHERE t.hop_count < 6
    AND NOT (e.target_node_id = ANY(t.node_path))
    AND n.status = 'active'
)
SELECT * FROM traverse WHERE hop_count >= 2;

The four detection rules

RuleLogicSeverity
DUPLICATE_FLOWTwo+ distinct Exp nodes each have a flow reaching the same Sys terminal. Check api_versions before flagging — version pairs are suppressed.HIGH
PASS_THROUGH_HOPA Proc node has out_degree == 1. It passes through to one downstream API with no orchestration.MEDIUM
DEEP_CHAINAny flow with hop_count >= 4. May indicate unnecessary intermediate steps.LOW
FAN_IN_CLUSTERA Sys node called by 3+ different Proc nodes. May be healthy reuse or accidental convergence.LOW

Critical implementation requirements

Transaction requirement: The Approve and Dismiss buttons must write the status update AND the audit_log row in a single transaction. If the status updates but the audit_log insert fails, you have an unaudited governance action.

# CORRECT — both writes in one transaction
with conn:
    with conn.cursor() as cur:
        cur.execute("UPDATE structural_findings SET review_status=%s WHERE finding_id=%s",
                    ('reviewed', finding_id))
        cur.execute("INSERT INTO audit_log "
                    "(entity_type, entity_id, action, comment, reviewer) "
                    "VALUES ('finding', %s, 'reviewed', %s, 'architect')",
                    (finding_id, comment))
# conn.__exit__ commits both or rolls back both

# WRONG — two separate commits, audit_log could be missed
conn.cursor().execute("UPDATE ...")
conn.commit()
conn.cursor().execute("INSERT INTO audit_log ...")
conn.commit()

M12 — Refresh, Snapshots & Audit Trail

Goal: A scheduled weekly job that re-runs traversal and detection, creates a graph_snapshots row, logs edge changes to edge_history, and diffs findings into new/resolved/persisting so architects can see what changed since last week.

Refresh job steps (in order)

1

Create ingestion_runs row

Insert with status='running'. All subsequent steps reference this run_id.

2

Reload nodes and edges

Re-ingest from source or detect changes. Update any changed purpose_text, owning_team, etc.

3

Edge diff → edge_history

Compare current api_edges to the previous run. New edges get event_type='appeared', removed edges get event_type='disappeared'.

4

Rebuild flows

Call materialize_flows(conn) — truncates and rebuilds the flows table.

5

Create graph_snapshots row

Insert with run_id, node_count, edge_count. UPDATE flows to set snapshot_id.

6

Re-run all four rules

Call run_all_rules(conn). Tag each new finding with the snapshot_id.

7

Finding diff

Compare new findings to previous snapshot. Tag each with detail['diff_status'] = 'new', 'persisting', or 'resolved'.

8

Close ingestion_runs row

UPDATE status='completed', completed_at=NOW().
