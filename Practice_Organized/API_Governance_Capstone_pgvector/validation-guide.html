Developer Guide

Validation Guide

API Governance & Discovery Platform

This guide explains how to validate every layer of the platform — ingestion quality, retrieval quality, composition correctness, and embedding quality — and how to determine whether fine-tuning is needed.

The four validation layers

Each layer must be validated in order. A problem at Layer 1 (ingestion) cascades into every higher layer — fixing retrieval quality before fixing ingestion is wasted effort.

Layer 1 — Ingestion quality          (fix first)
    ↓ only if Layer 1 passes
Layer 2 — Retrieval quality          (measure with labelled test set)
    ↓ only if Layer 2 passes
Layer 3 — Composition correctness    (architect review)
    ↓ only if Layer 3 passes
Layer 4 — Embedding quality          (UMAP + numeric gap)

Layer 1 — Ingestion Quality

What you're validating

The LLM-extracted purpose text and structured fields accurately describe what the real API does — not a generic placeholder.

Method: manual spot-check (not automatable)

Open the raw Bitbucket spec (or RAML/Swagger) for 15 randomly-selected APIs. For each, compare:

What to check Source of truth Red flag
purpose_text describes what the API actually does The RAML/Swagger description or README Generic text like "This is a microservice"
functionality correctly categorises the API The API's actual business function Mismatched (e.g. a payment API tagged as "customer")
domain is the canonical form The domain_taxonomy table Free-text variants ("Payments" vs "payments")
request_fields_structured lists the real request fields The RAML requestBody / Swagger parameters Missing fields, wrong types, wrong required flags
response_fields_structured lists the real response fields The RAML/Swagger responses Missing the actual fields the API returns

Acceptance threshold

13 out of 15 spot-checked APIs must pass all checks (87%). If below 87%: revise the LLM extraction prompt before proceeding.

The single most important check

Read the purpose_text out loud and ask: "If I searched for this API using these words, would I find it?" If the answer is no — if the text is too generic, too technical, or uses jargon that users would not type in a search box — the retrieval quality (Layer 2) will be poor regardless of the embedding model.

Running the automated checks from the practice notebook

-- Check 1: no nodes missing purpose embedding
SELECT project_name FROM api_nodes n
LEFT JOIN node_embeddings e ON e.node_id = n.node_id AND e.chunk_type = 'purpose'
WHERE n.status = 'active' AND e.embedding_id IS NULL;

-- Check 2: no nodes missing structured fields (composition validator is blind for these)
SELECT project_name FROM api_nodes n
LEFT JOIN api_fields f ON f.node_id = n.node_id
WHERE n.status = 'active' AND f.field_id IS NULL;

-- Check 3: no nodes with unresolved domain (free-text, not taxonomy-linked)
SELECT project_name FROM api_nodes WHERE domain_id IS NULL AND status = 'active';

All three queries must return zero rows before proceeding.

Layer 2 — Retrieval Quality

What you're validating

When a developer searches for a requirement, the correct API appears in the top results.

Method: labelled test set (create this yourself — it cannot be automated)

Step 1 — Create the test set before running any searches. Write 25-30 requirements in plain English. For each, write the correct answer (which API or APIs should be found). Do this based on your knowledge of the real APIs, not based on searching.

Requirement: "Process a NACH debit for a recurring subscription payment"
Correct answer: proc-nach-debit-api  (DIRECT_MATCH)

Requirement: "Validate a bank mandate and then initiate a debit"
Correct answer: proc-mandate-validate-api → proc-nach-debit-api  (COMPOSE)

Requirement: "Check available inventory for a product SKU before order"
Correct answer: proc-inventory-check-api  (DIRECT_MATCH)

Requirement: "Real-time machine learning fraud detection for transactions"
Correct answer: NEW_BUILD (no existing API)

Include at least: - 8-10 DIRECT_MATCH cases (clear single-API match) - 5-6 COMPOSE cases (need 2 APIs chained) - 3-4 NEW_BUILD cases (no existing coverage) - 2-3 edge cases (domain overlap, near-duplicates that should NOT match)

Step 2 — Run each requirement through the platform and record the result.

Step 3 — Measure recall@3 (is the correct answer in the top 3 results?)

Metric Formula Minimum threshold
Recall@1 Correct answer is result #1 60%
Recall@3 Correct answer is in top 3 72%
NEW_BUILD precision System correctly returns no match 75%

If recall@3 is below 72%

Work through this diagnosis in order:

  1. Is Layer 1 passing? Low-quality purpose_text is the most common cause of poor retrieval. Fix extraction before adjusting thresholds.

  2. Is the similarity threshold too high? Lower the threshold parameter in run_semantic_search() from 0.50 to 0.40 and re-measure.

  3. Is the embedding gap too low? Run Layer 4 verification. If gap < 0.10, the embeddings are not separating well enough — review purpose_text quality.

  4. Are the failing cases NEW_BUILD edge cases? If the correct answer is "no match" but the system returns a low-confidence DIRECT_MATCH, raise the DIRECT_MATCH threshold from 0.85 to 0.88.

Fine-tuning the embedding model is NOT the right answer at this stage. All failures at this scale are caused by data quality or threshold settings, not by the embedding model's capability.

Layer 3 — Composition Correctness

What you're validating

When the system recommends COMPOSE (two APIs chained), the proposed chain is actually valid and usable.

Method: architect review of first 20 COMPOSE recommendations

For each COMPOSE result in composition_candidates: 1. Read the LLM rationale 2. Review the field mapping table (which required fields are satisfied/unsatisfied) 3. Mark approved or rejected in the platform with a specific reason

Track the approval rate: approved / (approved + rejected).

Approval rate Meaning Action
≥ 70% Composition scoring is working well Proceed
50-70% Borderline — investigate rejected cases Adjust weights or schema_compat threshold
< 50% Scoring unreliable Review field_mappings quality first

Common reasons for rejection and fixes

Rejection reason Root cause Fix
"These APIs are in different domains and don't actually compose" domain_alignment weight too low Raise 0.25 → 0.35 in composition_confidence formula
"The field mapping is superficial — same name but different meaning" LLM field equivalence check not catching semantic differences Review llm_call_log for field_equivalence calls on these pairs
"API B is deprecated — should not be recommended" status filter missing in retrieval Confirm n.status = 'active' filter in all retrieval queries
"The schema compatibility score is high but the fields don't actually match" Leaf-name matching too aggressive for this domain Consider domain-specific exclusion list for common leaf names that appear across unrelated contexts (e.g. 'id', 'name', 'status')

Layer 4 — Embedding Quality

What you're validating

Semantically similar APIs actually cluster together in vector space, and dissimilar APIs are separated.

Method: UMAP plot + numeric gap check

Run the verification from the practice notebook Section 9 (Check 10) or the Embedding Health screen in the application.

# Expected output format
Within-domain similarity : 0.XXX
Cross-domain similarity  : 0.XXX
Gap (want > 0.10)        : 0.XXX

Interpreting results

Gap Meaning Action
> 0.20 Strong separation No action needed
0.10-0.20 Adequate Monitor on next bulk ingestion
0.05-0.10 Weak Review purpose_text quality (Layer 1 first)
< 0.05 Very weak Embeddings not useful for similarity — do not use Phase 2

When to run this check

  • After the initial bulk ingestion of real data
  • After any batch of 50+ new APIs are ingested
  • If users report that search results seem unrelated to their queries

Layer 5 — Graph Correctness

What you are validating

The edges in api_edges accurately reflect the real Mule call relationships — correct source/target nodes, correct endpoint paths, no missing edges. The four AI/data layers all assume the graph is correct. If edges are wrong or missing, every downstream feature — Phase 1 findings, impact analysis, duplicate flow detection — produces wrong answers silently. No error, just wrong results.

Method: manual flow trace (5 known flows)

Pick 5 complete flows you can verify independently — from Anypoint Studio, Mule runtime logs, or your own knowledge of the system. For each flow, walk it by hand and then query the database to confirm.

-- Confirm a known flow exists end-to-end
-- Example: exp-nach-debit-api -> proc-nach-debit-api -> sys-nach-clearance-api
SELECT
    src.project_name AS caller,
    e.source_endpoint_path,
    e.target_endpoint_path,
    tgt.project_name AS callee
FROM api_edges e
JOIN api_nodes src ON src.node_id = e.source_node_id
JOIN api_nodes tgt ON tgt.node_id = e.target_node_id
WHERE src.project_name = 'exp-nach-debit-api'
ORDER BY src.project_name;

-- Then confirm the next hop
SELECT
    src.project_name AS caller,
    e.source_endpoint_path,
    e.target_endpoint_path,
    tgt.project_name AS callee
FROM api_edges e
JOIN api_nodes src ON src.node_id = e.source_node_id
JOIN api_nodes tgt ON tgt.node_id = e.target_node_id
WHERE src.project_name = 'proc-nach-debit-api';

For each of your 5 known flows, confirm: - Every hop is present as an api_edges row - source_endpoint_path matches the actual calling endpoint - target_endpoint_path matches the actual downstream endpoint being called - No extra/wrong edges exist (the caller does NOT call APIs it shouldn't)

Acceptance threshold

5/5 known flows must be exactly correct — no partial credit. A missing edge is as bad as a wrong edge.

What to do if edges are wrong

Problem Root cause Fix
Edge completely missing Extraction step did not parse this call Review the Bitbucket extraction logic for HTTP client calls / DataWeave flows
Wrong source_endpoint_path Extraction picked up a different endpoint on the same API Review how the extraction identifies which endpoint initiates the call
Wrong target_endpoint_path Extraction used the wrong downstream path Check if the API has multiple versions or base paths
Extra edges that should not exist Extraction is too aggressive in finding HTTP calls Add a filter to exclude test/mock endpoints during extraction

The specific risk for Phase 1: pass-through hop detection depends on out-degree = 1. A missing edge makes a Proc look like a pass-through when it actually orchestrates multiple calls. Duplicate flow detection depends on both paths reaching the same terminal — a missing edge breaks the terminal entirely.

Layer 6 — Phase 1 Rule Correctness

What you are validating

The four structural rules (duplicate flow, pass-through hop, deep chain, fan-in cluster) produce genuine findings on real data — not false positives from versioning, and not missed findings you already know about.

Method: two checks

Check A — False positive rate

After the first run on real data, have 3 architects independently review the first 30 structural findings. For each finding they mark: - reviewed — this is a genuine redundancy/governance issue - dismissed — this is a false positive (version pair, healthy reuse, etc.)

Track the genuine rate: reviewed / (reviewed + dismissed).

Genuine rate Meaning Action
≥ 70% Rules are well-calibrated Proceed
50-70% Too many false positives Investigate dismissed findings — are they a specific pattern?
< 50% Rules need tuning Adjust thresholds (fan-in min_callers, deep_chain threshold)

Common false positive patterns and fixes:

Pattern Cause Fix
Version pairs flagged as duplicate flow api_versions check not working Verify M1b ran correctly — check api_versions table row count
Known shared-reuse Sys APIs flagged as fan-in Threshold too low Raise FAN_IN_THRESHOLD from 3 to 5 for production scale
One-step utility Procs flagged as pass-through Proc has real transformation logic, just one downstream call Add a has_transformation flag to api_nodes and exclude from pass-through detection
4-hop chains flagged as deep when they are legitimate Threshold too aggressive Raise DEEP_CHAIN_THRESHOLD from 4 to 5 for your architecture

Check B — False negative rate (known redundancy not detected)

From your own knowledge of the codebase, identify 3 APIs you already know are redundant or unnecessary. Confirm they appear in either structural_findings or merge_candidates.

If a known redundant pair is not detected: - Check if they are in the same domain (Phase 1 duplicate flow only fires if both paths reach the same terminal Sys API) - Check if the functional overlap is semantic rather than structural (Phase 1 is graph-shape only — semantic overlap appears in Phase 2) - If neither applies, the edges connecting them may be missing (go back to Layer 5)

Metric to track ongoing

-- False positive rate over time
SELECT
    review_status,
    COUNT(*) AS count,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 1) AS pct
FROM structural_findings
WHERE review_status IN ('open','reviewed','dismissed')
GROUP BY review_status;

Target: dismissed% stays below 30% after initial calibration.

Layer 7 — End-to-End Workflow (Audit Trail Integrity)

What you are validating

Every approve/reject/defer action correctly updates the target record AND writes an audit_log row. Without this, the platform is a read-only report tool — it cannot be used for actual governance decisions or audit evidence.

Method: walk each workflow action end-to-end

Run each of these manually and verify both the record update AND the audit log entry:

Test 1 — Structural finding review

-- Before: confirm finding is open
SELECT finding_id, review_status FROM structural_findings LIMIT 1;

-- Action: mark reviewed in the UI (or directly)
UPDATE structural_findings SET review_status = 'reviewed' WHERE finding_id = 1;
INSERT INTO audit_log (entity_type, entity_id, action, comment, reviewer)
VALUES ('finding', 1, 'reviewed', 'Confirmed duplicate — merge candidate raised', 'test-user');

-- Verify: both rows exist
SELECT review_status FROM structural_findings WHERE finding_id = 1;
SELECT * FROM audit_log WHERE entity_type = 'finding' AND entity_id = 1;

Test 2 — Merge candidate approval

SELECT candidate_id, status FROM merge_candidates LIMIT 1;

-- Approve via UI, then verify:
SELECT status FROM merge_candidates WHERE candidate_id = 1;
-- Must be 'approved'

SELECT entity_type, action, reviewer, acted_at
FROM audit_log
WHERE entity_type = 'merge_candidate' AND entity_id = 1;
-- Must exist with correct entity_type

Test 3 — Composition candidate approval

SELECT composition_id, status FROM composition_candidates LIMIT 1;

-- Approve via UI, verify:
SELECT status FROM composition_candidates WHERE composition_id = 1;
SELECT * FROM audit_log WHERE entity_type = 'composition_candidate';

Test 4 — Weekly refresh creates correct snapshot

-- After running the refresh job:
SELECT run_id, status, nodes_created, edges_created
FROM ingestion_runs ORDER BY started_at DESC LIMIT 1;

SELECT snapshot_id, node_count, edge_count
FROM graph_snapshots ORDER BY taken_at DESC LIMIT 1;

-- Flows from this run must be linked to the snapshot
SELECT COUNT(*) FROM flows WHERE snapshot_id = (
    SELECT snapshot_id FROM graph_snapshots ORDER BY taken_at DESC LIMIT 1
);
-- Must be > 0

-- Edge history written if any edges changed
SELECT event_type, COUNT(*) FROM edge_history
WHERE detected_in_run = (
    SELECT run_id FROM ingestion_runs ORDER BY started_at DESC LIMIT 1
)
GROUP BY event_type;

Test 5 — Retired API disappears from all queries

-- Mark one API as retired
UPDATE api_nodes SET status = 'retired' WHERE project_name = 'test-api-to-retire';

-- Confirm it disappears from discovery search results
SELECT * FROM node_embeddings e
JOIN api_nodes n ON n.node_id = e.node_id
WHERE n.project_name = 'test-api-to-retire' AND n.status = 'active';
-- Must return 0 rows (the retrieval queries all filter WHERE status = 'active')

-- Confirm it is excluded from traversal
SELECT * FROM flows f
JOIN api_nodes n ON n.node_id = f.root_exp_id
WHERE n.project_name = 'test-api-to-retire';
-- Should be 0 rows in the NEXT refresh run

Acceptance threshold

All 5 tests must pass completely — no partial credit. A missing audit_log row means governance decisions are not recorded and the platform cannot produce an audit trail for compliance purposes.

The most commonly missed failure

The status update and the audit_log insert are often written as two separate database calls. If the first succeeds and the second fails (network blip, constraint violation), you get a status update with no audit record. Both must be in the same transaction:

# Correct — both in one transaction
with conn:
    with conn.cursor() as cur:
        cur.execute("UPDATE merge_candidates SET status = %s WHERE candidate_id = %s",
                    ('approved', candidate_id))
        cur.execute("INSERT INTO audit_log "
                       "(entity_type, entity_id, action, comment, reviewer) "
                       "VALUES ('merge_candidate', %s, 'approved', %s, %s)",
                    (candidate_id, comment, reviewer))
# conn.__exit__ commits both or rolls back both

Layer 8 — LLM Consistency

What you are validating

The LLM produces consistent recommendations across repeated runs — because non-determinism in governance decisions destroys trust. An architect who gets DIRECT_MATCH on Monday and NEW_BUILD on Wednesday for the same requirement will stop trusting the platform.

Method: three consistency checks

Check A — Composition band stability

Run the same requirement 5 times and record the recommendation band each time:

requirement = "Process a NACH mandate debit for recurring payment collection"
bands = []
for i in range(5):
    results = analyze_requirement(requirement)
    bands.append(results[0]['recommendation'] if results else 'NO_RESULT')
print(bands)
# Expected: ['DIRECT_MATCH', 'DIRECT_MATCH', 'DIRECT_MATCH', 'DIRECT_MATCH', 'DIRECT_MATCH']
# Acceptable: max 1 variation across 5 runs

If the band changes more than once in 5 runs: lower temperature to 0.0 in the composition decision LLM call (currently 0.1 in 07-llm-integration-guide.md Section 6).

Check B — Field equivalence stability

Run the same borderline field pair 3 times:

for i in range(3):
    result = check_field_equivalence(
        "mandate_id", "string",
        "mandate_reference_id", "string",
        "payments"
    )
    print(f"Run {i+1}: equivalent={result['equivalent']}, confidence={result['confidence']:.2f}")
# Expected: same equivalent value all 3 times

If equivalent flips between true and false: lower temperature to 0.0 for field equivalence calls.

Check C — Query expansion paraphrase consistency

Two differently phrased versions of the same requirement should produce the same top result:

req_a = "initiate NACH debit for mandate"
req_b = "start NACH direct debit collection for a payment mandate"

result_a = semantic_search(req_a, top_k=1)
result_b = semantic_search(req_b, top_k=1)

top_a = result_a[0]['project_name'] if result_a else None
top_b = result_b[0]['project_name'] if result_b else None

print(f"Phrasing A top result: {top_a}")
print(f"Phrasing B top result: {top_b}")
print(f"Consistent: {top_a == top_b}")
# Expected: both return the same top API

If they differ: query expansion (LLM Point 1) is not bridging the gap. Check the expansion variants logged in llm_call_log for each query — confirm the variants are semantically covering the alternative phrasing.

Checking consistency via llm_call_log

-- Find all composition decisions for the same requirement
SELECT
    llm_response,
    called_at,
    latency_ms
FROM llm_call_log
WHERE call_type = 'composition_decision'
  AND user_prompt LIKE '%NACH mandate debit%'
ORDER BY called_at;

-- Check if recommendation band is consistent across runs
-- (parse llm_response JSON to extract the recommendation field)

Check Acceptable variance

Paraphrase consistency Top result matches in both phrasings

Go-live validation gate

Seven checks, all measured on real data, all must pass before the platform is opened to all developers:

Gate Layer Measurement Minimum threshold
Ingestion accuracy 1 Manual spot-check, 15 APIs 13/15 pass (87%)
Retrieval recall@3 2 Labelled test set, 25 requirements 18/25 correct (72%)
Composition approval rate 3 Architect review, first 20 COMPOSE results 14/20 approved (70%)
Embedding separation gap 4 UMAP numeric gap on real data Gap > 0.10
Graph correctness 5 Manual trace of 5 known flows 5/5 exactly correct
Phase 1 genuine rate 6 First 30 findings reviewed by architects ≥ 70% marked genuine
Audit trail integrity 7 5 end-to-end workflow tests 5/5 pass, all audit_log rows present
LLM band stability 8 Same requirement run 5 times Max 1 band variation

If any gate fails, fix at the layer where it broke — not at a lower layer.

When to fine-tune vs when to tune parameters

Symptom Fine-tune embedding model? Tune parameters instead
Low similarity gap (< 0.10) Only if purpose_text quality is already good Fix purpose_text extraction first
Wrong APIs in top results No Check similarity threshold, then purpose_text
COMPOSE recommendations rejected No Adjust composition weights and schema compat threshold
NEW_BUILD false positives No Raise DIRECT_MATCH threshold
System-wide poor performance after all tuning Only as last resort Requires a fine-tuning dataset you likely don't have

Fine-tuning the embedding model requires a training dataset of (query, relevant_API, irrelevant_API) triplets — minimum 500-1000 examples. You do not have this yet. All observed quality issues at this stage are parameter or data quality issues, not model capability issues.
