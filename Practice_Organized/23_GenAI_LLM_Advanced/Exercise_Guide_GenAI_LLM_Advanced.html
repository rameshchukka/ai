📘 Concept Notes

FAISS and approximate search

Exact nearest-neighbor search (IndexFlatL2) checks every vector — fine for small sets, too slow at millions of vectors. IVF-style indexes cluster vectors first and search only the most relevant clusters, trading a small accuracy loss for major speed gains.

Two-stage retrieval: search then re-rank

A fast, approximate retriever (embeddings) narrows millions of documents to a small shortlist; a slower, more accurate cross-encoder then re-scores just that shortlist — this two-stage design is standard in production search/RAG.

Observability isn't optional

Once an LLM feature is live, cost, latency, and quality issues are invisible unless you log them. Tracing every call's prompt, response, latency, and token cost is the foundation of debugging production LLM systems.

Prompt injection

Any text an LLM reads from an external source (a document, a web page, a tool's output) can contain text trying to hijack its behavior. Defense requires treating that content as untrusted data, not trusted instructions.

💡 Tips & Pitfalls

Tips

  • A cross-encoder re-ranker should run on a small shortlist, not the whole corpus.
  • Log every LLM call's prompt, response, latency, and cost from day one.
  • Treat any externally-sourced text as untrusted input.

Common Pitfalls

  • Fine-tuning when prompting/RAG would have solved the problem more cheaply.
  • Re-ranking the entire corpus instead of just the shortlist.
  • Trusting retrieved/tool-sourced content as if it were a trusted instruction.
