A2A Protocol: Zero to Hero

Agent Cards, discovery, the task lifecycle, sync/async exchange, multi-agent delegation, and security scoping.

📘 Concept Notes

A2A connects agents, MCP connects tools

MCP lets one agent use tools and data it controls. A2A lets one agent delegate a task to a genuinely separate, independently-operated agent — potentially a different vendor — whose internals stay a black box, like hiring an outside consultant instead of using an internal tool.

The Agent Card is the capability advertisement

Every A2A agent publishes a small JSON document listing its name, skills, and how to reach it. Other agents read this card to decide whether and how to delegate work — the A2A equivalent of an MCP server's tool list, but describing a whole agent.

Tasks move through a defined lifecycle

submitted -> working -> completed/failed/input-required. Messages coordinate the conversation about the task; artifacts are the actual deliverable produced. Long-running tasks use async submit+poll instead of blocking synchronous calls.

Trust boundaries require least-privilege input

Because A2A crosses organizational boundaries, you can't assume the same trust as an internal function call. Scope down to the minimum input a task needs, verify the remote agent's identity, and only delegate what you're willing to hand to an opaque system.

💡 Tips & Pitfalls

Tips

  • Check the Agent Card's skills before sending, then handle rejection anyway (defense in depth).
  • Scope input to the minimum a task needs — never pass full context 'just in case'.
  • Use async polling for anything that might take real time.

Common Pitfalls

  • Passing sensitive internal context across a trust boundary unnecessarily.
  • Assuming a remote agent completed successfully without checking task.state.
  • Blocking synchronously on a task that could run for minutes.

🌍 Real-World Use Cases

  • Multi-vendor agent ecosystems (different companies' agents collaborating)
  • Delegating specialized subtasks (translation, calculation, lookups) to dedicated agents
  • Building an orchestrator that composes independently-built agents
