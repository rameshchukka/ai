Vector Search at Scale: Zero to Hero

IVF, LSH, HNSW, and Product Quantization — the algorithms real vector databases run internally.

📘 Concept Notes

Brute force is correct but doesn't scale

Checking every vector for every query is O(n) — fine at 1,000 vectors, too slow at 100 million. Approximate Nearest Neighbor (ANN) algorithms trade a small amount of accuracy for massive speed by avoiding a full scan.

Every ANN method answers the same question differently

IVF pre-clusters vectors with k-Means and only searches the nearest few clusters. LSH hashes similar vectors into the same bucket using random hyperplanes. HNSW builds a navigable graph and greedily walks toward the query. Each is a different strategy for 'don't check everything, but check the right things'.

HNSW is the industry default for good reason

Graph-based search gives roughly logarithmic query time with strong recall, which is why FAISS, Pinecone, Chroma, and Weaviate all default to HNSW. It works by greedily walking a multi-layer graph from sparse long-range links down to dense local links.

Compression and clustering solve different bottlenecks

IVF solves the SPEED bottleneck by narrowing which vectors get compared. Product Quantization solves the MEMORY bottleneck by storing compressed codes instead of full floats. Production systems like FAISS's IndexIVFPQ combine both.

💡 Tips & Pitfalls

Tips

  • Start with brute force for correctness; move to HNSW as your default at scale.
  • Use IVF+PQ specifically when RAM is the binding constraint, not just speed.
  • Always measure recall@k against exact brute-force ground truth before trusting an index.

Common Pitfalls

  • Assuming ANN methods are always faster — at small scale brute force can win.
  • Forgetting PQ is lossy compression with a real accuracy cost.
  • Using n_probe=1 in IVF and being surprised by missed results near cluster boundaries.
