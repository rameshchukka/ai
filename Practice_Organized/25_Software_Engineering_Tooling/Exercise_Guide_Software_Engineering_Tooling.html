📘 Concept Notes

REST resource design

REST endpoints model nouns (resources), not verbs (actions): '/orders/{id}' with GET/POST/PUT/DELETE, rather than '/getOrder' or '/createOrder'. Status codes communicate outcome (200 OK, 201 Created, 404 Not Found, 204 No Content).

Caching (Redis-style)

An LRU (Least Recently Used) cache keeps a bounded set of the most recently accessed items, evicting the least recently used one when full — the same idea Redis and CPU caches use, just at different layers of a system.

Message queues decouple in time

A producer publishing to a queue doesn't need the consumer to be running right now — the message waits. This decoupling is the entire value proposition of Kafka/RabbitMQ-style systems, enabling independent scaling and failure isolation.

Design patterns solve specific pains

Singleton ensures exactly one shared instance (e.g. config). Factory centralizes object-creation logic. Observer lets many listeners react to one event without tight coupling. Each earns its complexity only when its specific pain is actually present.

💡 Tips & Pitfalls

Tips

  • Design REST endpoints around resources, not actions.
  • An LRU cache is the in-memory analog of what Redis provides as a service.
  • Test regex against messy real-world input, not just the clean example.

Common Pitfalls

  • Over-engineering a small script with design patterns it doesn't need.
  • Caching without an invalidation strategy — stale data served forever.
  • Regex that works on the happy path but breaks on real messy input.

🌍 Real-World Use Cases

  • Designing a clean internal API for an ML model-serving service
  • Caching repeated LLM/embedding calls to cut cost and latency
  • Extracting structured fields (emails, prices, dates) from unstructured text
