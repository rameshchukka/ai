01 What is RAG, and why

An LLM only knows what it saw in training — it can't know your documents, and it will confidently make things up. Retrieval-Augmented Generation fixes this: fetch relevant text first, then let the model answer using it.

The pipeline

question | v +----------------+ top-k relevant chunks +----------------+ | RETRIEVER | ---------------------------> | GENERATOR | | (search index) | | (LLM) | +----------------+ +----------------+ ^ | | v your documents grounded answer (chunked + embedded)

Why not just ask the LLM?

Three reasons: (1) it doesn't know your private/newer data; (2) it hallucinates when unsure; (3) retrieval lets you cite sources. RAG turns 'the model guesses' into 'the model answers from documents you retrieved'.

The three stages you'll master

StageQuestion it answersConcepts

Retrievalwhich chunks are relevant?BM25, semantic search, metrics

02 LLM calls & augmented prompts

The 'G' in RAG. Once you've retrieved context, you build a prompt that tells the model to answer from that context.

Anatomy of an augmented prompt

+-------------------------------------------------------+ | INSTRUCTIONS 'Answer using ONLY the context. If not | | in the context, say you dont know.' | +-------------------------------------------------------+ | CONTEXT - retrieved chunk 1 | | - retrieved chunk 2 | +-------------------------------------------------------+ | QUESTION 'How long do refunds take?' | +-------------------------------------------------------+ 
def build_prompt(question, context_docs):
    context = "\n".join(f"- {d}" for d in context_docs)
    return f"""Answer using ONLY the context below.
If the answer is not in the context, say you don't know.

CONTEXT:
{context}

QUESTION: {question}"""

The 'only the context' instruction is the anti-hallucination switch

Without it, the model blends the context with its own (possibly wrong) memory. With it, an answer that isn't supported forces an honest 'I don't know' — which is what you want in a bank or any high-stakes setting.

03 Embeddings & cosine similarity

To search by meaning, you turn text into a vector (a list of numbers) so that similar meanings sit close together. Closeness is measured by cosine similarity.

Text becomes a point in space

'refund my order' -> [0.12, 0.88, 0.03, ...] (a vector) 'get my money back' -> [0.10, 0.85, 0.05, ...] (nearly the same direction) 'track my package' -> [0.77, 0.04, 0.30, ...] (different direction) ^ dimension 2 | * refund | * money back <- close together = similar meaning | | * track +------------------------> dimension 1

Cosine = the angle between two vectors

cos(0deg) = 1.0 identical direction (most similar) cos(90deg) = 0.0 unrelated cos(180deg)= -1.0 opposite cosine = A . B / (|A| * |B|) (dot product over magnitudes) 
import numpy as np
def cosine(a, b):
    na, nb = np.linalg.norm(a), np.linalg.norm(b)
    return float(a @ b / (na * nb)) if na and nb else 0.0

Why cosine and not distance?

Cosine ignores magnitude (document length) and looks only at direction (which concepts). A short and a long document about refunds still point the same way — so cosine calls them similar, which is what you want.

Bag-of-words vs neural embeddings (important honesty)

The practice notebooks use a simple bag-of-words vectorizer so everything runs offline. Its limit: 'refund' and 'money back' share no words, so it scores them low. Real neural embeddings (Jina, OpenAI, sentence-transformers) learn that they mean the same thing and place them close. The cosine math is identical — only the vectors get smarter.

04 Retrieval — keyword (BM25) vs semantic

Two engines find relevant documents. BM25 matches exact words; semantic search matches meaning via embeddings. Experts use both.

QUERY: 'I want my money back' BM25 (keyword) SEMANTIC (embeddings) ------------- --------------------- looks for the words embeds the query, finds 'money','back' in docs docs with nearby vectors | | x misses 'refund' docs v finds 'refund' docs (no shared words) (learned they mean the same thing)

When each wins

BM25 (sparse)Semantic (dense)
Best atexact terms, codes, names, IDsparaphrases, synonyms, questions
Needs a model?noyes (an embedder)
Fails onreworded queriesrare exact strings it never learned
# semantic: rank documents by cosine to the query vector
def semantic_search(query, k=3):
    qv = vectorize(query, vocab)
    scored = [(doc_id[i], cosine(qv, doc_vecs[i])) for i in range(len(docs))]
    return sorted(scored, key=lambda x: -x[1])[:k]

Hybrid search = BM25 + semantic, fused

Since each catches what the other misses, production systems run both and combine the scores (often with a weight alpha, or reciprocal-rank fusion). That's the best-of-both approach you'll see in advanced modules.

05 Retrieval metrics — is retrieval any good?

You can't improve what you don't measure. These metrics score retrieval against labeled queries (queries where you know the right documents).

QUERY 'how do I get a refund' relevant = {d01, d02, d03} ranked results: rank 1 d03 RELEVANT rank 2 d01 RELEVANT rank 3 d21 no rank 4 d02 RELEVANT rank 5 d05 no

The formulas

Precision@K = (relevant in top K) / K -> falls as K grows Recall@K = (relevant in top K) / (total relevant) -> rises as K grows Reciprocal Rank (RR) = 1 / (rank of first relevant) MRR = average RR over all queries From the example above (relevant = 3): P@3 = 2/3 = 0.67 R@3 = 2/3 = 0.67 P@5 = 3/5 = 0.60 R@5 = 3/3 = 1.00 RR = 1/1 = 1.00 (first hit at rank 1) 
def precision_at_k(ranked, relevant, k):
    return sum(1 for d in ranked[:k] if d in relevant) / k

def recall_at_k(ranked, relevant, k):
    return sum(1 for d in ranked[:k] if d in relevant) / len(relevant)

def reciprocal_rank(ranked, relevant):
    for i, d in enumerate(ranked, 1):
        if d in relevant: return 1.0 / i
    return 0.0

Which metric when

P@1 / MRR when there's one right answer (did the best doc rank first?). Recall@K when several docs are relevant (did we find them all?). P@K falls, R@K rises as K grows — that tension is the whole game.

06 Chunking — how you split matters most

You retrieve pieces, not whole documents. How you cut them decides retrieval quality more than almost any other choice.

Fixed-size, and why overlap helps

no overlap: [====chunk A====][====chunk B====] ^ an idea split HERE is lost from both overlap: [====chunk A====] [====chunk B====] <- B repeats A's tail, so the boundary idea survives

Recursive (variable) splitting — respect natural boundaries

try to split on the BIGGEST boundary that fits: paragraph -> sentence -> word -> hard cut so chunks end at sentence boundaries, not mid-word. 
def chunk_fixed(text, size, overlap=0):
    words = text.split(); step = max(1, size - overlap); out = []
    i = 0
    while i < len(words):
        out.append(" ".join(words[i:i+size])); i += step
    return out

The trade-offs

ChoiceEffect
smaller chunksprecise matches, but may lose surrounding context
larger chunksmore context, but noisier retrieval (dilutes the match)
more overlapsaves boundary ideas, at the cost of some duplication
recursivecoherent chunks (whole sentences), slightly more complex

07 Vector databases

A vector database stores your embedded chunks and finds the nearest ones to a query fast, even over millions of documents. Chroma, Weaviate, pgvector, FAISS, Pinecone are all vector stores.

INDEXING (once) QUERY TIME (every question) --------------- -------------------------- chunk -> embed -> store ------> embed query -> nearest-vector search (+ metadata) | (approximate, fast) v top-k chunks (+ optional metadata filter)

Metadata filtering — the underrated superpower

Besides the vector, you store fields (topic, date, source, method). Then you can filter before or with the semantic search: 'find refund-like chunks WHERE topic=payments'. Exact filters + fuzzy meaning together = precise retrieval. Your course uses Weaviate for this; your other work used Chroma and pgvector — same idea, different engines.

08 LLM generation parameters

Once context is in the prompt, these knobs control how the model generates — how random, how focused, how long.

Temperature — randomness

temperature = 0 always pick the most likely next word (focused, repeatable) temperature = 1 sample naturally (balanced) temperature = 1.5+ flatten probabilities (creative, risky)

top_p (nucleus) and top_k — which words are even allowed

next-word probabilities: the .35 a .20 an .10 cat .08 ... (long tail) top_k = 3 -> only consider {the, a, an} (k most likely) top_p = 0.9 -> consider the smallest set whose probabilities sum to 0.90 (the 'nucleus')

How they combine

top_k/top_p first restrict the candidate words; temperature then controls how randomly you pick among them. For factual RAG answers use low temperature (0–0.3) so the model sticks to the retrieved facts; for brainstorming, raise it.

# typical settings for a factual RAG answer
params = {"temperature": 0.0, "top_p": 1.0, "max_tokens": 300}
# the model will answer as deterministically as possible from the context

09 Prompt engineering & structured output

Small changes to the prompt change the output a lot. Two high-value skills: guiding the model with examples, and forcing structured (parseable) output.

Zero-shot vs few-shot

zero-shot: 'Classify sentiment: "the shoes are great"' -> model guesses the format few-shot: 'Review: "awful fit" -> negative Review: "love these" -> positive Review: "the shoes are great" ->' -> model copies the shown format exactly

Structured output — get JSON, not prose

WITHOUT structure: 'The item is a gift, arrives in 5 days.' (must parse text) WITH structure: {"gift": true, "delivery_days": 5} (already usable) 
# modern models take a schema and RETURN a typed object
from pydantic import BaseModel
class Extract(BaseModel):
    gift: bool
    delivery_days: int
result = model.with_structured_output(Extract).invoke(prompt)
result.delivery_days   # a real int, no manual parsing

Why structured output matters in RAG

When the next step is code (route this query, filter by this field, store this record), you need data, not a paragraph. Structured output turns the LLM into a reliable component in a pipeline instead of a text blob you have to scrape.

10 Routing — multiple knowledge sources

Real assistants have several sources (FAQ, products, policies). Routing decides which to search so each query hits the right index.

+--> [ FAQ retriever ] --+ query --> ROUTER +--> [ Product retriever ] --+--> generator --> answer +--> [ Policy retriever ] --+ router = a classifier: 'is this FAQ, product, or policy?' (an LLM, or similarity to each source's description) 
def route(query):
    qv = vectorize(query, vocab)
    faq_sim  = max(cosine(qv, v) for v in faq_vecs)
    prod_sim = max(cosine(qv, v) for v in product_vecs)
    return "FAQ" if faq_sim >= prod_sim else "PRODUCT"

Routing = less noise, better answers

Searching every source for every query drags in irrelevant chunks. Routing scopes the search — the same idea as metadata filtering, but choosing an entire source rather than a field.

11 Observability — tracing a RAG system

In production you must see what happened: which chunks were retrieved, what prompt was sent, how long it took, what it cost. That's tracing.

Spans and traces

a TRACE = one full request, made of nested SPANS (timed steps): TRACE: answer('how do I get a refund') [ 1.4s ] |-- SPAN retrieve [ 0.2s ] -> 3 chunks |-- SPAN build_prompt [ 0.0s ] +-- SPAN llm_generate [ 1.2s ] -> 180 tokens

Why it matters

When an answer is wrong, tracing tells you WHERE: did retrieval fetch the wrong chunks, or did the model ignore good context? Without traces you're guessing. Tools like Phoenix (your course's tool), LangSmith, or OpenTelemetry capture this.

# conceptually: wrap each stage in a span
with tracer.start_span("retrieve") as s:
    chunks = retrieve(query); s.set_attribute("num_chunks", len(chunks))
with tracer.start_span("llm_generate") as s:
    answer = llm(prompt); s.set_attribute("tokens", count_tokens(answer))

Cost & latency tracking

Spans record token counts and timings, so you can compute cost-per-query and find the slow step. This is how you decide what to optimize — measure, don't guess.

12 Putting it all together — the expert view

Every concept above is one box in a single, evaluable, observable pipeline.

INDEX (offline) RETRIEVE GENERATE -------------- -------- -------- docs query augmented |-- chunk (05) |-- embed (03) prompt (02) |-- embed (03) |-- BM25 + semantic |-- LLM params (08) +-- store in vector DB (07) | (04, hybrid) +-- structured out (09) (+ metadata) |-- route (10) | +-- filter (07) v answer \_______________________ MEASURE (metrics 04) ______/ \_______________________ OBSERVE (tracing 11) ______/

The expert habit: measure → change → re-measure

Never ship a change you can't show helped. Fix an eval set of labeled queries, compute P@K/R@K (and answer quality), change one thing (chunking, k, hybrid weight, prompt), re-measure. Tracing tells you which stage to change; metrics tell you if it worked.
