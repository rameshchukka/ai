01 TF-IDF — weighting words by how informative they are

Plain word-counts treat every word equally. TF-IDF downweights common words and upweights rare, distinctive ones — the classic step between raw counts and BM25.

TF (term frequency) = how often the word appears in THIS doc IDF (inverse doc freq) = log( total docs / docs containing the word ) -> big for RARE words, ~0 for words in every doc TF-IDF = TF * IDF -> 'refund' (rare) scores high; 'the' (everywhere) ~ 0 
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity
vec = TfidfVectorizer()
X = vec.fit_transform(docs)          # docs x terms, TF-IDF weighted
sims = cosine_similarity(vec.transform([query]), X).ravel()

TF-IDF → BM25

BM25 is TF-IDF plus two refinements: saturation (the 10th occurrence of a word adds less than the 2nd) and length normalization (long docs don't win just by being long). Learn TF-IDF for the intuition; use BM25 in production. Both are sparse/keyword methods — they need shared words, so a pure synonym is missed (that's what dense embeddings fix).

02 ANN & HNSW — fast search at scale

Exact nearest-neighbor search compares the query to every vector — impossible at millions of docs. Approximate Nearest Neighbor (ANN) trades a sliver of accuracy for enormous speed. HNSW is the ANN algorithm your vector DBs use.

The scaling problem

exact (brute force): compare to ALL N vectors -> time grows with N (O(N)) ANN: smartly skip most of them -> ~O(log N), ~1-5% off

HNSW = Hierarchical Navigable Small World graph

layer 2 (sparse): o-------------o-------------o long-range 'express' links \ | / layer 1: o--o--o--o--o--o--o--o--o--o medium links |\ |/ |\ |/ |\ |/ |\ |/ | layer 0 (all vecs): o-o-o-o-o-o-o-o-o-o-o-o-o-o-o every vector, short links SEARCH: enter at the top, greedily hop toward the query, drop a layer, repeat. Big jumps first (top), fine steps last (bottom) -> reaches the answer fast.

The knobs your vector DB exposes (Chroma, Weaviate, pgvector)

M = links per node (denser graph → better recall, more memory). ef_construction = build-time effort (better graph, slower build). ef (search) = query-time effort (higher → better recall, slower query). If recall is poor, raise ef first.

Why 'approximate' is fine

you accept ~1-5% of neighbors being slightly off in exchange for 100-1000x speed. Almost always the right trade for RAG.

03 Cross-encoders & reranking

Vector retrieval is fast but coarse. A cross-encoder re-scores the top candidates much more accurately by reading the query and document together. This is the retrieve-then-rerank pattern.

BI-ENCODER (retrieval) CROSS-ENCODER (reranking) ---------------------- ------------------------- query -> [vec_q] (query, doc) --> ONE model --> score doc -> [vec_d] (separately) sees both TOGETHER -> far more accurate score = cosine(vec_q, vec_d) FAST: docs embedded once, offline SLOW: run the model per (query,doc) pair -> can index millions -> only feasible on the top ~20-50

The pipeline

query --> [ bi-encoder / vector search ] --> top 50 candidates | v [ cross-encoder reranker ] --> re-ordered top 5 --> LLM 
# real cross-encoder (needs the model):
from sentence_transformers import CrossEncoder
ce = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
scores = ce.predict([(query, doc) for doc in candidates])
reranked = [d for _, d in sorted(zip(scores, candidates), reverse=True)]

The rule

Retrieve wide and cheap (bi-encoder, top 50), then rerank narrow and accurate (cross-encoder, top 5). Reranking usually gives the biggest precision boost per unit of effort in a RAG system. Never rerank the whole corpus — far too slow.

04 ColBERT — late interaction (token-level)

Between bi-encoders (one vector per doc, fast/coarse) and cross-encoders (joint, accurate/slow) sits ColBERT: keep one vector per token and match at the token level. This is 'late interaction'.

bi-encoder: whole doc -> ONE vector (word detail averaged away) ColBERT: each token -> its OWN vector (word detail kept) MaxSim scoring: for each QUERY token, find its BEST-matching DOC token, then SUM those maxima.
query: [waterproof] [jacket] doc: [this][jacket][is][waterproof][and][windproof] waterproof -> best doc match 'waterproof' 1.0 jacket -> best doc match 'jacket' 1.0 MaxSim = 1.0 + 1.0 = 2.0

Where it fits

ColBERT is more accurate than a single-vector bi-encoder and far more scalable than a cross-encoder (the token vectors are precomputed offline; only the cheap MaxSim runs at query time). The cost is storage — many vectors per document. Your course's rag-colbert lab and the LangChain book both include it.

accuracy: bi-encoder < ColBERT < cross-encoder speed/scale:cross-encoder < ColBERT < bi-encoder ColBERT is the balanced middle.

05 Retrieval metrics — more of them, worked

Six metrics, all computed from the same ranked list + relevance labels — each a different lens. Worked on one example so you can verify every number.

relevant = {A, B, C} ranked: 1:A(rel) 2:X 3:B(rel) 4:Y 5:C(rel)
MetricFormula (worked)Answers
P@Krel in top-K / K  → P@3 = 2/3 = .667of top-K, how many relevant?
R@Krel in top-K / total rel  → R@3 = 2/3 = .667of all relevant, how many found?
MRR1 / rank of first hit  → 1/1 = 1.0how high is the first hit?
MAPavg P@k at each hit  → (1 + .667 + .6)/3 = .756are ALL relevant ranked high?
nDCGDCG / ideal-DCG  → .885graded + order-aware quality
F1@K2·P·R/(P+R)  → F1@3 = .667one number balancing P & R

nDCG deserves a closer look (it's the one people ask about)

DCG = sum_i rel_i / log2(i+1) (a hit at rank 5 counts less than at rank 1) IDCG = DCG of the PERFECT ordering (all relevant first) nDCG = DCG / IDCG in [0,1] (1.0 = ideal ranking) Unlike P/R (relevant or not), nDCG allows GRADED relevance: rel = 3 (perfect), 2 (good), 1 (ok), 0 (irrelevant) and it PENALIZES putting good docs low. 
import numpy as np
def dcg(rels): return sum(r/np.log2(i+2) for i,r in enumerate(rels))
ndcg = dcg(gains) / dcg(sorted(gains, reverse=True))

Choosing a metric

One right answer → MRR / P@1. Several right answers, order matters → MAP. Graded relevance (some docs 'more' relevant) → nDCG. One balanced number → F1. Coverage → Recall@K. Report a few, not one — they tell different stories.

06 Observing results better with Chroma Studio

Numbers tell you that retrieval is good or bad; Chroma Studio shows you why. Here's how to use its views to diagnose each advanced concept above.

Map each concept to a Studio view

To see…In Chroma StudioWhat good/bad looks like

Near-duplicates (dilute ranking)Visualize → stacked pointspoints on top of each other → dedupe them

Cluster structure (ANN neighborhoods)Visualize → KMeans clustertight clusters are what HNSW navigates quickly

A concrete diagnosis workflow

1. Metrics say recall is low. (from notebook 05) 2. Open Chroma Studio -> Search the failing query. 3. Are the right docs NEAR the top but below junk? yes -> a RERANKER (cross-encoder, sec 03) will fix ordering. 4. Are the right docs MISSING from results entirely? yes -> retrieval problem: check chunking, try hybrid (BM25+dense), or raise ef (sec 02) if it's an ANN recall issue. 5. Visualize -> color by topic: do the query's topic docs even cluster? no -> embeddings/chunking are the root cause, not ranking.

Why visual + metrics together

A P@K number is a verdict with no explanation. Chroma Studio's Visualize/Search/Browse turn that verdict into a cause: wrong ordering (rerank), missing docs (retrieval/chunking), or tangled topics (embeddings). You change the right thing instead of guessing.

Connect it to your metadata features

Studio's metadata summary + structured filter (which you built earlier) let you confirm whether a topic is under-represented (thin coverage → low recall for that topic) or whether filtering to one topic sharpens results — both directly explain metric movements.
