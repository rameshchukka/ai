M1L1 Extract Structured JSON from Restaurant Text

The foundational skill: turn messy free text into clean, typed JSON with an LLM — the 'structured output' idea that everything downstream depends on.

Concept — why structured extraction matters

Downstream steps (vector indexing, filtering, MCP tools) need fields, not prose. An LLM reads each restaurant paragraph and returns {name, cuisine, location, ...} — converting unstructured text into data your pipeline can query.

step

Step by step

restaurant_data = open("California-Culinary-Map.txt").read()
restaurant_list = restaurant_data.split("\n\n")[1:]   # one paragraph per restaurant

def llm_model(system_msg, prompt_txt):
    model = ModelInference(model_id="ibm/granite-3-8b-instruct",
                           project_id="skills-network", credentials=Credentials(...))
    return model.generate(...)   # returns the model text

# loop each restaurant -> prompt the LLM to emit JSON -> parse -> collect
  • 1. Read the text file, split on blank lines into one string per restaurant, drop the header.
  • 2. llm_model() wraps WatsonX: pick the Granite model, pass a system message ('you extract JSON') + the restaurant text.
  • 3. Loop each restaurant, prompt for JSON, json.loads() the reply, append to a list.
  • 4. Save the list to structured_restaurant_data.json — this file feeds Modules 2 and 4.
tip Understand the system prompt — it's what forces JSON. If parsing fails, the model added prose; tightening the system message ('return ONLY valid JSON, no markdown') fixes it. This is the same structured-output skill from LangChain, done with WatsonX here.

A multimodal model takes an image (and a prompt) and returns text — e.g. a caption or a description. This turns images into text you can embed and search, unlocking image data for RAG.

M2L1 Construct a Multimodal Vector Index

The heart of RAG: embed text AND images into a vector store (Chroma) so you can search by meaning across both modalities.

Concept — two embedders, one index

Text and images live in different vector spaces, so you use TWO models: sentence-transformers (384-d) for article/caption text, and CLIP (512-d) for images. Each becomes a Chroma collection. CLIP is special — it embeds images AND text into a shared space, enabling text→image search later.

step

Step by step

from sentence_transformers import SentenceTransformer
from transformers import CLIPModel, CLIPProcessor
from langchain_chroma import Chroma

text_embedder  = SentenceTransformer(...)      # 384-d, for article text
clip_model     = CLIPModel.from_pretrained(...) # 512-d, for images

article_db = Chroma(collection_name="restaurant_articles", persist_directory=DB_DIR)
image_db   = Chroma(collection_name="food_images", persist_directory=DB_DIR)
# upsert embeddings + metadata (doc_id, image_path, fields) into each collection
  • 1. Prepare the image dataset (download/unzip) and load the structured data from M1.
  • 2. Initialize the two embedders — note the dimensions (384 text, 512 image) MUST match each collection.
  • 3. Build Document objects carrying text + metadata (doc_id, image_path, cuisine…).
  • 4. upsert embeddings + metadata into two Chroma collections that persist to disk.
  • The metadata is what enables filtering in the next lab — store it now.
tip This is your RAG_Course indexing stage, multimodal: load → embed → store, but with a second (image) embedder. The dimension-must-match rule is the same gotcha as your pgvector work.

M2L2 Similarity Retrieval with Metadata Filtering

Query the index by meaning, then narrow with metadata filters — precise retrieval.

Concept — semantic search + metadata filter together

Embed the query, find nearest vectors (semantic), AND constrain by metadata (e.g. cuisine='Italian') — the combination that makes retrieval precise instead of just 'semantically close'. Exactly the 'underrated superpower' from your foundations.

step

Step by step

def retrieve_articles(query, k=5, where=None):
    qv = text_embedder.encode([query])
    return article_db.similarity_search_by_vector(qv, k=k, filter=where)

# Demo 1: no filter  -> pure semantic
# Demo 2: with where={"cuisine": "Italian"} -> semantic WITHIN a category
  • 1. Validate the DB exists and re-init the SAME embedders (must match how you indexed).
  • 2. Write retrieval utilities for articles (text embedder) and images (CLIP).
  • 3. Demo 1: search with no filter — see raw semantic results.
  • 4. Demo 2: add a metadata where filter — see results scoped to a category.
  • Compare the two demos: the filter removes semantically-close-but-wrong-category hits.
tip If retrieval returns nonsense, the #1 cause is using a DIFFERENT embedder than you indexed with — dimensions/space won't match. Always re-init the exact same models.

M2L3 Multimodal Similarity Fusion and Reranking

Combine text AND image similarity into one ranked list, then rerank — advanced multimodal retrieval.

Concept — fusion + reranking

A query can match on text (the article) and on images (CLIP text→image). Fusion combines the two score lists into one ranking (like hybrid search, but across modalities). Reranking then reorders the fused candidates for final precision — the retrieve-then-rerank pattern applied to multimodal.

step

Step by step

# text->articles  AND  text->images (CLIP shared space)
article_hits = retrieve_articles(query, k=10)
image_hits   = retrieve_images(query, k=10)     # CLIP embeds the TEXT query into image space
# fuse the two scored lists (normalize + combine), then rerank the top candidates
  • 1. Verify both Chroma collections and re-init both embedders.
  • 2. Define two retrieval functions: text→articles and text→images (CLIP lets a text query search images).
  • 3. Fuse: normalize the two similarity scores and merge into one ranked list.
  • 4. Rerank the fused top candidates; Demo 1 no filter, later demos add metadata filters.
  • This is the multimodal, capstone-level version of hybrid search + reranking.
tip The elegant trick: CLIP embeds the text query into the SAME space as images, so 'spicy noodle dish' can retrieve matching food photos with no captions needed. Fusion balances that against the text-article matches.

M4 MCP — Server, Client & LLM Host (Model Context Protocol)

Module 4 is the agentic capstone: expose your data/tools over MCP, build a client that calls them, then an LLM host that uses them as tools.

Concept — what MCP is and why it matters

Model Context Protocol (MCP) is a standard way to expose resources (data) and tools (functions) so any MCP-aware LLM/agent can discover and call them. It decouples your tools from any one model — build the tool once, any MCP host can use it. This is the agentic-AI backbone (and part of what AWS Bedrock's agent ecosystem is converging toward).

step

M4L1 — Build an MCP Server (server.py, FastMCP)

from fastmcp import FastMCP
mcp = FastMCP("Connoisseur-Server")

@mcp.resource("culinary-map://california")
def get_culinary_map() -> str: ...        # exposes raw data

@mcp.tool()
def search_restaurants(cuisine: str) -> list: ...   # a callable tool
  • Resource (@mcp.resource) = read-only data an agent can fetch (the culinary map).
  • Tool (@mcp.tool()) = a function an agent can call with arguments (search restaurants, get details). Three tools in this lab.
  • Run the FastMCP server locally; test.py exercises it. Read lab-instructions.md.
  • The docstring on each tool is how the LLM knows when to use it — same rule as LangChain tools.
step

M4L2 — Build & Test an MCP Client (client.py)

# client.py connects to the server, LISTS its tools/resources,
# and CALLS them programmatically -> proves the protocol works end to end
  • The client discovers what the server exposes (tools + resources) and invokes them.
  • test_demo2.py validates the round-trip. This is the 'consume an MCP service' side.
  • Concept: discovery + typed calls are what let ANY agent use your server without custom glue.
step

M4L3 — Design an LLM MCP Host (app.py)

# app.py = an LLM that USES the MCP tools to answer questions.
# The LLM decides which tool to call, calls it via MCP, reads the result, answers.
  • This is the full agentic loop: user question → LLM reasons → calls an MCP tool → gets data → answers. The LLM is the 'host', MCP is how it reaches tools.
  • It ties the whole certificate together: M1 made the data, M2 indexed it, M4 exposes + uses it agentically.
  • This is the pattern behind production agent systems — tools as MCP services an LLM orchestrates.
tip Run order: server (M4L1) must be running before the client (M4L2) or host (M4L3) can connect. Read each folder's lab-instructions.md — they give the exact terminal commands.

★ How the whole certificate connects

It's one capstone project on the California Culinary Map dataset:

M1  EXTRACT   text -> structured JSON   +   images -> captions   (build clean data)
         |
M2  INDEX     embed text (384-d) + images (CLIP 512-d) -> Chroma   (make it searchable)
         |     retrieve + metadata filter -> multimodal fusion + rerank
         |
M4  SERVE     expose data+tools over MCP -> client calls them -> LLM host uses them (agentic)

The through-line for the exam & your job

Extract → Index → Retrieve → Serve-as-tools. This mirrors real RAG-to-agentic systems: structure your data, make it retrievable, then let an LLM use it through a standard protocol (MCP). On AWS this maps onto Bedrock Knowledge Bases (index/retrieve) + Bedrock Agents/tools (serve) — the same shape you'll see in AIP-C01.
