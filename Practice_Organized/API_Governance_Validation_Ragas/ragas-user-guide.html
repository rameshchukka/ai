RAGAS User Guide

This guide is for architects and tech leads who need to interpret RAGAS results and make decisions based on them — without necessarily understanding the implementation details.

What RAGAS tells you

RAGAS answers six specific questions about the API Discovery and Composition features. Each question has a threshold — a minimum score the platform must reach before it is trustworthy for governance decisions.

MetricPlain English questionPass threshold
Context PrecisionWhen a developer searches, does the right API appear near the top?≥ 0.70
Context RecallFor requirements needing 2 APIs, does the search find both of them?≥ 0.70
Answer RelevancyIs the first search result actually relevant to what was asked?≥ 0.60
FaithfulnessDoes the AI rationale only say things that are true about the found APIs?≥ 0.80
Answer CorrectnessDoes the DIRECT_MATCH / COMPOSE / NEW_BUILD decision match expert judgement?≥ 0.75
Context Entity RecallAre the API names that should appear actually mentioned in results?≥ 0.80

The bottom line

If all six metrics are green, the AI features are performing well enough for architects to trust the search results and composition recommendations as a starting point for governance decisions. Architects must still review and approve — RAGAS tells you the platform is reliable enough to be worth reviewing.

If Faithfulness is below 0.80, the AI rationale is making claims that are not supported by the actual API data. Do NOT use the Composition Advisor recommendations for governance decisions until this is resolved. The structural findings and merge candidates (which are not LLM-generated) are unaffected.

  PASS=6  FAIL=0  SKIP=0

  STATUS: ALL RAGAS METRICS PASS

All six green. Platform is ready for production use of AI features.

Example output — retrieval problem

  [X] FAIL  Context Precision             0.542  (min 0.70)
  [X] FAIL  Context Recall                0.619  (min 0.70)
  [v] PASS  Answer Relevancy (LLM)        0.688  (min 0.60)
  [v] PASS  Faithfulness                  0.844  (min 0.80)
  [X] FAIL  Answer Correctness (Band)     0.647  (min 0.75)
  [X] FAIL  Context Entity Recall         0.712  (min 0.80)

What this means: The AI rationale is faithful (0.844) and relevance is fine when something IS retrieved (0.688), but the retrieval itself is poor — correct APIs are not being ranked first (Precision 0.542) and sometimes not retrieved at all (Recall 0.619). This drags down Answer Correctness because the wrong APIs feed the composition formula.

Action: Fix the embeddings or purpose_text quality. Do not adjust the composition formula thresholds — the formula is working correctly with bad inputs.

Example output — hallucination problem

  [v] PASS  Context Precision             0.751
  [v] PASS  Context Recall                0.794
  [v] PASS  Answer Relevancy (LLM)        0.712
  [X] FAIL  Faithfulness                  0.641  (min 0.80)
  [v] PASS  Answer Correctness (Band)     0.788
  [v] PASS  Context Entity Recall         0.853

What this means: Retrieval is excellent and the band decision is correct, but the LLM rationale is inventing claims not supported by the actual API data. Faithfulness at 0.641 means 36% of claims in rationales are hallucinated.

Action: Tighten the composition decision prompt in core/llm.py. Add: "Only make claims explicitly supported by the API context provided. Do not infer capabilities not stated in purpose_text or functionality." Do not re-embed or tune retrieval — that is not the problem.

What SKIP means

  [-] SKIP  Faithfulness                  0.000  SKIPPED - no LLM configured

The metric was not run because the LLM endpoint was not configured. SKIP metrics do not count as pass or fail. Configure INTERNAL_LLM_URL in the config cell and re-run to get a full evaluation.

What to Do When Metrics Fail

Each failing metric points to a specific stage of the pipeline and a specific fix. This page gives the decision tree for each failure pattern.

Context Precision fails (< 0.70)

The correct API IS being retrieved but is not ranked first.

  1. Check the purpose_text for the top-ranked (wrong) API vs the correct API. Is the wrong API's purpose_text more generic — covering the domain broadly while the correct API is domain-specific? Generic purpose_text pulls in wrong APIs.
  2. Ask the data team to make purpose_text more specific: "orchestrates NACH debit — validates mandate, checks limits, submits to clearance" beats "payment processing API".
  3. Re-embed and re-run sections 2 and 3 only.

Context Recall fails (< 0.70)

The correct API is not appearing in the retrieved top-5 at all.

  1. For the failing samples, manually run: retrieve the query and check positions 6-10. If the correct API appears at position 7, the fix is lowering the similarity threshold from 0.40 to 0.30.
  2. If the correct API does not appear anywhere in the results: check its purpose_text. Is it too short or too generic? A purpose_text of "API" with 3 words will not embed well.
  3. For COMPOSE failures specifically: are both APIs in the same domain? If they span domains, domain alignment score may be dragging the correct pair below the COMPOSE threshold.

Answer Relevancy fails (< 0.60)

The LLM is judging the top retrieved API as not relevant.

  1. Review the actual (question, top_api) pairs that scored below 0.60. Print them from the notebook.
  2. If the API IS relevant but LLM scored it low: the LLM scoring prompt may be too strict. Review the ANSWER_RELEVANCY_PROMPT.
  3. If the API genuinely IS NOT relevant: retrieval problem — see Context Precision and Recall fixes above.

Faithfulness fails (< 0.80)

The LLM is adding claims to rationales that are not in the API data.

  1. Look at the printed claims for failing rationales. Which type of claim is being hallucinated most? (e.g. field names, business rules, performance claims?)
  2. Update the composition decision prompt in core/llm.py LLM Point 3. Add an explicit constraint like: "Your rationale must ONLY reference the API names, purpose descriptions, and functionality listed above. Do not add business rules, field names, or performance characteristics that are not in the context."
  3. Re-run M6b to regenerate rationales. Re-run Section 5 only.

Answer Correctness fails (< 0.75)

The DIRECT_MATCH / COMPOSE / NEW_BUILD band is wrong.

  1. Look at the confusion matrix. Is the failure mostly DIRECT_MATCH being classified as COMPOSE? Or COMPOSE being classified as NEW_BUILD?
  2. DIRECT_MATCH → COMPOSE confusion: the DIRECT_MATCH threshold (default 0.85) may be too high. Lower to 0.80 in core/composition.py.
  3. COMPOSE → NEW_BUILD confusion: the COMPOSE threshold (default 0.60) may be too high. Lower to 0.55.
  4. DIRECT_MATCH → NEW_BUILD confusion (maximum error): retrieval is failing to find the correct API at all. Return to Context Recall fix.

Context Entity Recall fails (< 0.80)

Ground truth API names are not surfacing in the retrieved context text.

  1. The most common cause: the API's project_name is not mentioned anywhere in its purpose_text. The embedding is built from purpose_text — if the name is not there, it cannot surface in a text-based entity check.
  2. Fix: update the extraction prompt to include the project_name in purpose_text: "proc-nach-debit-api orchestrates NACH debit..." rather than just "Orchestrates NACH debit..."
  3. Re-embed after updating purpose_text, then re-run Section 7 only.

When to Run RAGAS

RAGAS is not a one-time check — it is a continuous quality measurement. This page defines the schedule and triggers.

Scheduled runs

WhenWhat to runWhy
Before go-liveFull RAGAS suite (all 6 metrics)Gate: all metrics must pass before AI features are opened to developers
Monthly (ongoing)Sections 2, 3, 6, 7 (no LLM metrics)Check if retrieval quality has drifted as new APIs are ingested
Quarterly (ongoing)Full RAGAS suiteFull quality audit including LLM-based metrics
After re-embeddingFull RAGAS suiteEmbedding change affects all retrieval metrics
After purpose_text updatesSections 2, 3, 7 (retrieval metrics)Purpose_text change affects ranking and entity recall
After LLM prompt updatesSections 5, 6 (faithfulness, correctness)Prompt change affects LLM output quality

Drift detection

Track metric scores over time. A metric that was 0.74 in January and is 0.62 in April indicates drift — not a configuration change but a gradual degradation as the API inventory grows or changes.

Common causes of metric drift:

  • Context Precision drifting down: New APIs have been ingested with generic purpose_text, competing with specific APIs for top positions
  • Faithfulness drifting down: The LLM model version was updated and the new version is more prone to adding context not in the retrieved APIs
  • Answer Correctness drifting down: New requirement types that the current thresholds handle poorly — may need threshold recalibration

Adding new requirements to EVAL_DATASET

Every quarter, add 5-10 new requirements from real developer queries. Developers often search for capabilities that were not in the original dataset — these become the hardest cases for the platform. A platform that gets 0.85 on the original dataset but 0.60 on new queries has overfitted to the original test set.
