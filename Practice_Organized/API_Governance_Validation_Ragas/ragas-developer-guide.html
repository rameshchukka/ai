Building the Evaluation Dataset

The EVAL_DATASET in Section 1 is the most important thing you fill in. Bad evaluation data produces misleading metrics. Good evaluation data produces actionable diagnostics.

Rules for writing evaluation samples

Never look up search results before writing the ground truth. Write what the correct answer SHOULD be from your knowledge of the APIs. Then run the evaluation. If you write ground truth after seeing results, you are measuring your ability to read results, not the platform's quality.

1

Write DIRECT_MATCH samples (target: 10+)

Requirements that you know, from your architectural knowledge, map to exactly one existing API. The question should be phrased as a developer would actually type it — not as an API description. Good: "process recurring mandate debit for customer account". Bad: "call proc-nach-debit-api".

2

Write COMPOSE samples (target: 4+)

Requirements where two APIs must be chained. Both correct API names must be in ground_truth_apis. The ground_truth_answer should explain how they chain: "validate mandate first, then initiate the debit".

3

Write NEW_BUILD samples (target: 3+)

Requirements with no existing API coverage. These test false positive rate — the platform should not return a confident DIRECT_MATCH for a capability that does not exist. Use capabilities you know are missing: ML fraud scoring, real-time risk assessment, image processing, etc.

4

Add edge cases (target: 2+)

Requirements that sound similar to an existing API but should NOT match. Set expected_band: "NEW_BUILD" and add the false-positive candidate to should_not_match. Tests whether the platform over-retrieves semantically adjacent but functionally different APIs.

Minimum dataset size

EVAL_DATASET size recommendations:
  Minimum viable  : 17 samples (10 DM + 4 COMPOSE + 3 NB)
  Good coverage   : 30 samples (15 DM + 8 COMPOSE + 5 NB + 2 edge)
  Full confidence : 50+ samples across all domains

Below 17 samples, metric variance is too high to be actionable.
At 17 samples, a 5% metric change = 1 sample — borderline reliable.
At 30+ samples, metrics are stable enough to track over time.

How Each Metric is Implemented

This page documents exactly what the notebook computes for each metric, so you can audit the code and adjust if needed.

Context Precision — implementation detail

def context_precision(retrieved_names, ground_truth_names):
    relevant   = set(ground_truth_names)
    precisions = []
    hits        = 0
    for k, name in enumerate(retrieved_names, 1):   # k=1,2,3,4,5
        if name in relevant:
            hits += 1
            precisions.append(hits / k)   # precision at this position
    return mean(precisions) if precisions else 0.0

Example: ground truth = ["proc-nach-debit-api"], retrieved = ["some-other-api", "proc-nach-debit-api", ...]

  • k=1: "some-other-api" — not relevant, no entry
  • k=2: "proc-nach-debit-api" — relevant! hits=1, precision@2 = 1/2 = 0.50
  • Result: CP = 0.50 (correct API retrieved but not ranked first)

If "proc-nach-debit-api" were at k=1: CP = 1.0

Faithfulness — implementation detail

Two LLM calls per rationale:

  1. Claims extraction: LLM reads the rationale and returns a JSON array of specific, verifiable claims
  2. Claims verification: For each claim, LLM checks whether the claim is supported by the retrieved API context (purpose_text + functionality)

Faithfulness = supported_claims / total_claims

Cost note: A rationale with 5 claims uses 1 + 5 = 6 LLM calls. With 10 rationales: ~60 LLM calls. Run Faithfulness on a subset if cost is a concern — the first 10 rationales in merge_candidates are sufficient for calibration.

Answer Correctness — partial credit

ADJACENCY_CREDIT = {
    ("DIRECT_MATCH", "COMPOSE"): 0.5,   # adjacent bands
    ("COMPOSE", "DIRECT_MATCH"): 0.5,
    ("COMPOSE", "NEW_BUILD"):    0.5,
    ("NEW_BUILD", "COMPOSE"):    0.5,
    ("DIRECT_MATCH", "NEW_BUILD"): 0.0, # maximum error
    ("NEW_BUILD", "DIRECT_MATCH"): 0.0,
}

Exact match = 1.0. Adjacent mismatch = 0.5. Maximum mismatch = 0.0.

This partial credit scheme means a mean Answer Correctness of 0.75 could be: all exact matches on 75% of samples, or a mix where some samples have 0.5 partial credit.

Look at the confusion matrix output to distinguish — an all-0.5-partial platform behaves very differently from a 75%-exact platform even if the mean score is the same.

Adding custom metrics

To add a new metric, follow this pattern:

# New metric: Response Completeness
# Measures whether the rationale covers all aspects of the requirement

def response_completeness(question, rationale):
    if not INTERNAL_LLM_URL or not rationale:
        return 0.0
    prompt = (
        "Does this rationale completely address all aspects of the requirement?\n"
        f"Requirement: {question}\nRationale: {rationale}\n"
        'Score 1-5 where 5=completely addresses all aspects.\n'
        'Return only JSON: {"score": N}'
    )
    resp  = call_llm("Evaluate completeness.", prompt)
    data  = json.loads(resp)
    return (data["score"] - 1) / 4.0

The only structural difference between the two RAGAS notebooks is the retrieval function. All metric computation is identical.

What this means for metrics

Because all metrics use the same retrieve_pgvector() function name and return format, all metric cells (Sections 2-8) are byte-for-byte identical between the two notebooks.

You may see slightly different metric scores between pgvector and ChromaDB variants even with the same embedding model and data. This is because:

  • pgvector uses HNSW approximate nearest-neighbour search — fast but approximate
  • ChromaDB also uses HNSW internally with different default parameters (m=16 by default)
  • For the same query the ranking order may differ by 1-2 positions at the margin

If the Context Precision score differs significantly between variants (more than 0.05), inspect the specific cases that differ. The difference reveals which HNSW configuration is more accurately ranking the true top-1 result.

Comparing both variants

To compare pgvector vs ChromaDB objectively, run both RAGAS notebooks with the SAME EVAL_DATASET and compare the Context Precision and Context Recall scores. The better performing variant on your specific data distribution is the right long-term choice.

# Run in both notebooks, then compare:
pgvector_results = {
    "Context Precision": 0.74,
    "Context Recall":    0.82,
    "Answer Correctness": 0.76,
}
