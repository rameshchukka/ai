RAGAS Fundamentals

RAGAS (Retrieval Augmented Generation Assessment) is an evaluation framework specifically designed to measure RAG pipeline quality. It does not treat the system as a black box — it measures each stage separately.

Why standard metrics are not enough

Before RAGAS, teams measured RAG systems with simple accuracy: "did the final answer match the expected answer?" This misses the real diagnostic question: why did it fail?

Failure typeStandard accuracyRAGAS diagnoses
Retrieved the wrong APIsFails — but you don't know whyContext Precision + Recall identify the retrieval failure specifically
Retrieved the right APIs but ranked them badlyFails — but looks like retrieval failureContext Precision low, Recall high — ranking problem, not embedding problem
Retrieved correctly but LLM made up extra claimsMay pass — answer looks rightFaithfulness catches hallucinated rationale even when the band is correct
Correct band but wrong APIs named in rationalePasses — band matchesContext Entity Recall catches this

The RAG pipeline stages

This platform has a 4-stage RAG pipeline. RAGAS measures each stage:

Stage 1: QUERY PROCESSING
  Developer types: "process recurring NACH mandate debit"
  LLM Point 1 expands to 3 semantic variants
       |
       ↓ Measure: does expansion help retrieval? (Context Precision pre/post)

Stage 2: RETRIEVAL
  pgvector/ChromaDB returns top-5 APIs by cosine similarity
       |
       ↓ Measure: Context Precision, Context Recall, Context Entity Recall

Stage 3: SCORING
  Deterministic formula: 0.40*similarity + 0.35*schema + 0.25*domain
       |
       ↓ Measure: Answer Correctness (does the band match ground truth?)

Stage 4: LLM GENERATION
  LLM Point 3 writes the rationale for the recommendation
       |
       ↓ Measure: Faithfulness (is rationale grounded in retrieved APIs?)
            Answer Relevancy (does the top result actually address the query?)

The six RAGAS metrics for this platform

1. Context Precision

Are the CORRECT APIs ranked at the TOP of the retrieved list? A system that retrieves the right API at position 5 is worse than one that retrieves it at position 1, even though both "recalled" it.

CP = mean(precision@k for each k where a relevant item appears)

Threshold: ≥ 0.70 — if below, the ranking function needs tuning, not the embedding model. Check if better purpose_text phrasing moves the correct API higher.

2. Context Recall

Are ALL correct APIs present somewhere in the retrieved top-K results? For COMPOSE requirements, both APIs must be retrieved — missing one means the composition cannot be proposed.

CR = |ground_truth_apis ∩ retrieved_apis| / |ground_truth_apis|

Threshold: ≥ 0.70 — if below and Context Precision is fine, the issue is coverage, not ranking. Lower the similarity threshold or increase top_k.

3. Answer Relevancy

Does the TOP retrieved API actually address the developer's requirement? This is scored by the LLM (1-5 scale, normalised to 0-1), not by string matching. Catches cases where a topically-adjacent but functionally-different API is returned.

AR = LLM_score(question, top_retrieved_api_context) / 4 [1-5 → 0-1]

Threshold: ≥ 0.60 — lower threshold than precision because there is inherent subjectivity in relevance judgement at the boundary.

4. Faithfulness

Does the LLM rationale (in merge_candidates.llm_rationale and composition_candidates.llm_rationale) only make claims that are supported by the retrieved API context? Catches hallucination.

F = supported_claims / total_claims_in_rationale

Threshold: ≥ 0.80 — high threshold because faithfulness violations destroy architect trust. A rationale that says "this API processes payments" when the API is actually a customer lookup is a serious failure.

5. Answer Correctness (Band Accuracy)

Does the DIRECT_MATCH / COMPOSE / NEW_BUILD recommendation match the ground truth? This is the end-to-end quality metric — it reflects the combined quality of embedding + scoring + LLM decision.

AC = exact_match(predicted_band, ground_truth_band) [partial credit for adjacent bands]

Threshold: ≥ 0.75 — 75% of requirements should get the correct band. DIRECT_MATCH ↔ COMPOSE confusions score 0.5 (adjacent bands). DIRECT_MATCH ↔ NEW_BUILD scores 0.0 (maximum error).

6. Context Entity Recall

Are the ground-truth API names actually mentioned in the retrieved context text? Simpler and faster than full context recall — checks surface form rather than semantics. A low score here with high Context Recall means the right APIs are retrieved but their names are not in the purpose_text being embedded.

CER = apis_named_in_context / |ground_truth_apis|

Threshold: ≥ 0.80 — API names should be in purpose_text. If not, update the extraction prompt to include the project_name in purpose_text.

RAGAS vs Standard Validation

This platform uses both standard validation (8 layers) and RAGAS. They are complementary, not redundant. Understanding when to use each prevents double-counting effort.

What each covers

CheckStandard validationRAGAS
Schema correctnessLayer 1 automated checkNot covered
Graph correctnessLayer 5 flow traceNot covered
Audit trail integrityLayer 7 workflow testsNot covered
Structural finding qualityLayer 6 architect reviewNot covered
LLM band stabilityLayer 8 (5 runs, same band)Answer Correctness (ground truth comparison)
Retrieval recallLayer 2 recall@K (binary hit)Context Precision + Recall (ranked quality)
Composition qualityLayer 3 architect reviewFaithfulness + Answer Correctness
LLM output groundingNot coveredFaithfulness
Ranking qualityNot coveredContext Precision
Relevance (LLM-judged)Not coveredAnswer Relevancy

Rule: Standard validation covers the infrastructure and governance layers. RAGAS covers the AI quality layers. Run standard validation first (it is faster and has no LLM cost). Only run RAGAS after all 8 standard layers pass.

Sequencing

1

Run 01-automated-checks.ipynb (standard)

Verify schema, ingestion counts, embedding coverage, graph correctness, audit trail. These are pre-conditions for RAGAS — if the embeddings are not even populated, RAGAS metrics are meaningless.

2

Run 02-retrieval-labelled-test.ipynb (standard)

Quick binary recall@K check. If recall@3 is below 72%, fix retrieval before running RAGAS — RAGAS will just confirm the same problem with more detail.

3

Build EVAL_DATASET for RAGAS

This takes time to do properly. Write 17+ requirements from your own knowledge before running any searches. The dataset is reusable across future RAGAS runs.

4

Run 04-ragas-evaluation.ipynb

Run sections 2-7 in order. LLM-based metrics (Answer Relevancy, Faithfulness) will incur LLM API calls — roughly 2-5 calls per sample per metric.

5

Act on failures

Each metric failure points to a specific stage of the pipeline. See the Diagnosis Guide in the Fundamentals overview for the fix per metric.

Thresholds & Calibration

All thresholds in the RAGAS notebook are starting points, not fixed rules. This page explains how to adjust them for your specific platform at full scale.

Default thresholds and their rationale

MetricDefaultWhy this number
Context Precision0.70Balances strictness against the reality that COMPOSE requirements have two correct APIs — ranking both in top-2 out of 5 is realistic
Context Recall0.70Same reasoning — COMPOSE cases where only 1 of 2 APIs is retrieved are partial credit (0.50) not zero
Answer Relevancy0.60LLM scoring has inherent variance — 0.60 sets a floor without requiring near-perfect relevance for every query
Faithfulness0.80High threshold because hallucinated rationale is the most damaging quality failure — it causes architects to distrust the platform
Answer Correctness0.7575% band accuracy means 3 in 4 requirements get the correct DIRECT_MATCH/COMPOSE/NEW_BUILD classification — consistent with the composition formula calibration
Context Entity Recall0.80API names should almost always be retrievable in context — a low score here is a data quality issue not a model issue

Adjusting after initial run

Wait until you have run RAGAS on at least 30 real requirements before adjusting thresholds. Early runs with small datasets have high variance — a single outlier can move a metric by 0.10 or more.

When to raise a threshold

  • Your platform consistently scores 0.85+ on a metric — the threshold is too easy
  • The platform is being used for high-stakes architecture decisions — raise Faithfulness to 0.90
  • Architects are complaining about wrong-band recommendations — raise Answer Correctness to 0.85

When to lower a threshold

  • A metric is consistently failing despite the underlying retrieval being correct — the threshold may be miscalibrated for your domain
  • Context Precision failing because you have many semantically similar APIs in one domain — this is a hard retrieval problem, not a threshold problem, but lowering to 0.60 while you improve embeddings is pragmatic
