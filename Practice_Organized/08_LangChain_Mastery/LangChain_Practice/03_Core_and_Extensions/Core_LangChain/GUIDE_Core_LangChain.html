01 Concepts

RAG, three times, peeling away the framework

You build the same retrieval-augmented pipeline pure-Python first, then with LangChain+FAISS, then LangChain+Chroma. Each step hides more machinery — so you learn what .from_documents() and .as_retriever() actually do, because you wrote the equivalent by hand.

02 Setup

  1. Copy .env.office.example (org) or .env.personal.example to .env.
  2. pip install langchain langchain-community faiss-cpu chromadb (plus your provider).
  3. llm_provider.py bridges your in-house models — no HuggingFace download needed.

03 Step-by-step with expected output

exercise

rag_pure_python.py

Do: run it, then print the intermediate values — the chunk list, one embedding's length, and the similarity scores for a query.

✔ Worked answer / expected output

You'll see: text split into N chunks; each chunk embedded to a fixed-length vector; a query scored against every chunk by cosine; the top chunk(s) passed to the LLM; a grounded answer printed. No LangChain anywhere — this is the ground truth of what RAG is.

Do: run it and match each LangChain call to the hand-written step it replaces.

✔ Worked answer / expected output

Same answer as the pure-Python version, far fewer lines. FAISS.from_documents(docs, embeddings) = (embed all chunks + build an index); .as_retriever() = (the cosine-search step). FAISS is in-memory, so nothing persists after the process ends.

exercise

rag_langchain_chroma.py

Do: run it twice. Note the second run doesn't re-embed if the Chroma directory already exists.

✔ Worked answer / expected output

Same answer again, but now the vector store persists in a folder — reopen it later without re-embedding. This is the production shape: Chroma adds persistence, metadata filtering, and delete-by-id over FAISS.

04 Exercises + worked answers (from learning_guide.md)

exercise A

Vary chunk_size / overlap in the pure-Python script

✔ Worked answer / expected output

Smaller chunks → more precise matches but may split an idea across chunks (recall drops). Larger chunks → more context per hit but noisier. Overlap recovers answers that sit on a boundary. There's no universal best — it depends on your documents.

exercise B

Swap the demo text for a real PDF (PyPDFLoader) + your questions

✔ Worked answer / expected output

The pipeline is unchanged except the loader; retrieval quality now depends on the PDF's structure. Scanned PDFs need OCR first — a common real-world gotcha.

exercise C

FAISS vs Chroma head-to-head

✔ Worked answer / expected output

Same top results (same embeddings + cosine). Differences are operational: Chroma persists and filters by metadata; FAISS is faster to stand up but in-memory. Choose by whether you need persistence/metadata.

exercise D

Add a second in-house LLM, compare on the same retrieved chunks

✔ Worked answer / expected output

Retrieval is identical (same chunks); only generation differs. A larger model usually gives more complete answers. Holding retrieval fixed while varying the LLM is exactly how you isolate a generation problem from a retrieval problem.
