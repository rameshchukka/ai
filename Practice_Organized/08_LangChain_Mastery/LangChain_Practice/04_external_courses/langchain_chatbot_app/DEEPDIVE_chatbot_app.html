01 What this is — a real deployable app

Unlike the notebook tutorials, this is a production-shaped RAG service: a FastAPI backend + a Streamlit UI, with document ingestion, multi-model chat, and source citations. The best way to learn it is to trace one request through the layers — which this guide does with the real code.

The stack

FastAPI (the API, port 9091) · Streamlit (the web UI) · Pinecone (the vector store) · OpenAI + Anthropic (chat + embeddings). Modern LangChain 0.1.x — current imports, no version gymnastics.

The one idea to hold onto

Two flows share one handler. Ingest puts documents into Pinecone; chat retrieves from Pinecone and generates an answer. Everything else is plumbing around those two flows.

03 How it starts up

code walkthrough

app.py — the FastAPI app wires in the routers

app = FastAPI()
from endpoints import ingest, chat
for endpoint in [ingest, chat]:
    app.include_router(endpoint.router)
uvicorn.run("app:app", port=9091, reload=True)
  • FastAPI is created once; each endpoint file exposes a router that's plugged in.
  • The server listens on port 9091 — the UI posts to localhost:9091.
code walkthrough

startup.py — run API + UI together

def run_app():       subprocess.run(["python3", "app.py"])
def run_streamlit(): subprocess.run(["streamlit", "run", "ui/main.py"])
# each in its own thread, started together
  • One command launches both processes in parallel threads — the backend and the web UI.
  • This is why you run python startup.py, not the files individually.

04 Flow 1 — Ingestion (getting documents in)

Trace an upload: UI → /ingest → handler → Pinecone.

code walkthrough

endpoints/ingest.py — the entry point

@router.post("/ingest")
async def ingest_documents(files: List[UploadFile], namespace: Optional[str] = Form(None)):
    handler = BaseHandler()
    documents = handler.load_documents(files, namespace)
    handler.ingest_documents(documents)
    return {"message": "Documents ingested"}
  • Accepts uploaded files (and an optional namespace — a way to keep separate document sets in one Pinecone index).
  • Delegates the real work to two handler methods: load_documents then ingest_documents.
code walkthrough

handlers/base.py :: load_documents — file type → loader

loader_map = {"txt": TextLoader, "pdf": PyMuPDFLoader, "docx": Docx2txtLoader}
for file in files:
    ext = file.filename.split(".")[-1]
    if ext not in loader_map: raise HTTPException(400, "File type not permitted")
    # write to a temp file, then load with the right loader
    loader = loader_map[ext](temp.name)
    documents.append(loader.load())
  • A loader map picks the right LangChain loader per extension — the clean way to support many formats.
  • It validates the extension (security: reject unknown types) and streams the upload to a temp file before loading.
code walkthrough

handlers/base.py :: ingest_documents — split, embed, store

splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)
for document in documents:
    chunks = splitter.split_documents(document)
    Pinecone.from_documents(chunks, self.embeddings,
                            index_name=self.pinecone_index, namespace=...)
  • This is the RAG indexing half: chunk (1000 chars, 100 overlap) → embed → store in Pinecone.
  • Embeddings are OpenAI text-embedding-3-small (1536-dim) by default, or -large (3072-dim) — the code warns that Pinecone's index dimension MUST match.
  • Note the splitter map: the app supports ~18 splitter types; recursive is the default. This is exactly the chunking concept from your foundations, made configurable.

05 Flow 2 — Chat (answering from documents)

Trace a question: UI → /chat → handler → retrieve + generate → answer with sources.

code walkthrough

endpoints/chat.py — validate, then delegate

class ChatModel(BaseModel):
    query: str
    model: str = "gpt-3.5-turbo"
    temperature: float
    vector_fetch_k: Optional[int] = 5     # how many chunks to retrieve
    chat_history: list[str] = []
    namespace: Optional[str] = None

# validate model name and temperature (0.0-2.0), then:
handler = BaseHandler(chat_model=chat_model.model, openai_chat_temperature=chat_model.temperature)
response = handler.chat(chat_model.query, chat_model.chat_history,
                        namespace=..., search_kwargs={"k": chat_model.vector_fetch_k})
  • A Pydantic model (ChatModel) defines and validates the request body — the FastAPI way to get typed, checked inputs for free.
  • It guards the inputs (valid model name, temperature in range) before doing any work — good API hygiene.
  • vector_fetch_k = how many chunks to retrieve (the 'k' in top-k). namespace scopes retrieval to one document set.
code walkthrough

handlers/base.py :: chat — the RAG generation core

vectorstore = Pinecone.from_existing_index(index_name=self.pinecone_index,
                                           embedding=self.embeddings, namespace=...)
retriever = vectorstore.as_retriever(search_kwargs={"k": 5})
bot = ConversationalRetrievalChain.from_llm(
        self.llm_map[self.chat_model],   # the chosen LLM (OpenAI or Anthropic)
        retriever,
        return_source_documents=True)
result = bot.invoke({"question": query, "chat_history": chat_history})
  • ConversationalRetrievalChain is the key object: it (1) reformulates the question using chat history, (2) retrieves relevant chunks, (3) generates a grounded answer.
  • return_source_documents=True is why the UI can show citations — the chunks that supported the answer come back too.
  • self.llm_map[self.chat_model] — a dict mapping model names to constructors, so the SAME code serves GPT-4, GPT-3.5, or Claude. Clean multi-provider design.

Why ConversationalRetrievalChain (not plain RetrievalQA)

It handles follow-up questions. If you ask 'what about its cost?' it uses the chat history to rewrite that into a standalone question ('what about the cost of X?') before retrieving — so retrieval works even when the query is only meaningful in context.

06 The UI layer

code walkthrough

ui/main.py — a thin Streamlit form over the API

api_endpoint = "http://localhost:9091/chat"
param1 = st.text_input("Query")
model_selector = st.selectbox("Chat Model", [...])
temperature = st.slider("Temperature", 0.0, 2.0, 0.7)
source_documents = st.slider("Number of Source Documents", 1, 10, 5)
if st.button("Send"):
    data = post_data(api_endpoint, {...})
    st.markdown(data["response"]["answer"])
    for msg in data["response"]["source_documents"]:
        st.markdown(f"Document: {msg['metadata']['source']} ...")
  • The UI holds NO logic — it just collects inputs, POSTs to the API, and renders the answer + source documents. Clean separation: UI ↔ API ↔ handler.
  • The sliders map directly to the API's temperature and vector_fetch_k — you can watch how each affects answers.
  • Showing source documents under each answer is a trust feature — users see WHERE the answer came from.

07 Running it yourself

Prerequisites

An OpenAI key (billing), an Anthropic key (for the Claude models), and a Pinecone account + index. Copy example.env to .env and fill OPENAI_API_KEY, ANTHROPIC_API_KEY, PINECONE_API_KEY, PINECONE_ENV, PINECONE_INDEX.

  1. pip install poetry            (this app uses Poetry, not plain pip)
  2. poetry install                (reads pyproject.toml / poetry.lock)
  3. poetry shell                  (enter the environment)
  4. cp example.env .env  + fill in your keys
  5. python startup.py             (launches API + Streamlit together)
  6. open the Streamlit URL, upload a doc, then ask questions

Pinecone dimension gotcha

Your Pinecone index's dimension MUST match the embedding model: 1536 for text-embedding-3-small (default), 3072 for text-embedding-3-large. Mismatch → ingest fails with an ApiException (the code even warns about this).

Org-network / offline note

This app is hard-wired to cloud services (OpenAI, Anthropic, Pinecone) — all likely blocked on your org network. To run it, use a personal machine, OR adapt it: swap Pinecone for local Chroma and the OpenAI lines for your in-house wrapper. The structure (FastAPI + handler + UI) stays identical.
