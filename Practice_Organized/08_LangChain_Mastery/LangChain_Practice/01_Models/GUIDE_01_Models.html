01 Concepts you need first

A 'model' in LangChain is one of three things

LLM (text-in, text-out — legacy completion style), Chat model (messages-in, message-out — what everything uses now), and Embedding model (text-in, vector-out — powers search/RAG). This folder has one small script per kind and per provider so you can see them side by side.

Why the uniform interface matters

Every chat model exposes .invoke(messages); every embedder exposes .embed_query() / .embed_documents(). So switching OpenAI → Anthropic → Google → local is a one-line change. Prove that to yourself and provider lock-in stops scaring you.

02 Setup for this folder

  1. From the bundle root, activate your venv (see DEVELOPMENT_GUIDE.html).
  2. pip install -r 01_Models/requirements.txt (or the base stack).
  3. Copy your keys into 01_Models/.env — the scripts call load_dotenv(). Or avoid keys entirely with the two *_hf_local.py scripts.

03 Walkthrough — Chat models

exercise

chatmodel_openai.py / _anthropic.py / _google.py

Concept: instantiate a provider's chat model, call .invoke() with a prompt, print the reply. Note the constructor params: temperature (0 = deterministic, higher = more random) and max_completion_tokens (length cap).

Steps: read the model line → run → read the printed reply → change temperature and re-run.

✔ Worked answer / expected output

Each prints an AIMessage whose .content is the answer. With temperature=0 re-runs are near-identical; with temperature=1.5 (as in the OpenAI script) wording varies each run. The OpenAI script caps at max_completion_tokens=10, so its reply is deliberately truncated — that's expected, not a bug.

exercise

chatmodel_hf_api.py

Concept: the same chat interface, but the model runs on HuggingFace's hosted endpoint (needs HUGGINGFACEHUB_API_TOKEN). Shows LangChain wrapping a non-OpenAI provider.

✔ Worked answer / expected output

Prints a model reply via the HF Inference API. If it errors with a 401/permission, your token is missing or the model is gated. On the org network this call may be blocked — use chatmodel_hf_local.py instead.

exercise

chatmodel_hf_local.py

Concept: run a small HuggingFace model locally via HuggingFacePipeline — no API, no per-call cost. First run downloads the model to HF_HOME.

✔ Worked answer / expected output

First run is slow (downloads weights); later runs are fast and fully offline. Output quality is lower than the cloud models — expected for a small local model. This is your offline-safe fallback when APIs are blocked.

exercise

init_chat_model.py

Concept: init_chat_model("provider:model") — a single helper that returns any provider's chat model, so you don't import a different class each time.

✔ Worked answer / expected output

Prints a reply identical in shape to the per-provider scripts. The lesson: this one helper replaces all the provider-specific constructors — the cleanest way to stay provider-agnostic.

04 Walkthrough — Embedding models

exercise

embedding_openai_query*.py & embedding_openai_docs.py

Concept: turn text into a vector. embed_query() for one string, embed_documents() for many. Note the dimensions param (e.g. 32 or 300) — smaller = cheaper/faster, larger = more expressive.

✔ Worked answer / expected output

Prints a Python list of floats. Length equals the dimensions you asked for (32 → a 32-number list; 300 → 300). embed_documents prints a list of such vectors, one per input document.

exercise

embedding_Gemini_query.py

Concept: same embedding interface, Google's model.

✔ Worked answer / expected output

Prints a float vector for the query. Different provider, identical calling pattern — the point of the uniform interface.

exercise

embedding_hf_local.py

Concept: local all-MiniLM-L6-v2 embeddings (384-dim), offline after first download.

✔ Worked answer / expected output

Prints 384-length vectors. No API key needed. This is the embedder to use on the org network when HuggingFace Hub is reachable once for the initial download.

capstone

document_similarity.py

Concept — this is RAG in miniature: embed several documents and a query, compute cosine similarity, return the closest document. Everything in your Chroma/pgvector work is this, scaled up.

Steps: run it → read which document it picks as most similar → change the query to match a different document → confirm the pick changes.

✔ Worked answer / expected output

Prints the document most similar to the query plus a similarity score. Ask about a topic clearly in one document and that document wins with the highest score. This is exactly retrieve-by-meaning — the kernel of every RAG system you've built.
