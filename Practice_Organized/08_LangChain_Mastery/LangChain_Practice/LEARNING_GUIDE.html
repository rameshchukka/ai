01 Fundamentals to know BEFORE these exercises

These six modules assume a handful of ideas. Get these and the code reads easily.

1 · A model call: .invoke()

Every LangChain model exposes .invoke(input) → run once. These modules use Google Gemini via ChatGoogleGenerativeAI. Swapping to OpenAI/Anthropic/your in-house model is a one-line change; the rest is identical.

2 · Prompt templates

PromptTemplate(template='... {topic} ...', input_variables=['topic']) — reusable prompts with named slots, filled at call time. The building block of every chain here.

3 · LCEL — the pipe operator |

LangChain Expression Language composes steps with |: prompt | model | parser. Output of each flows into the next. This one operator is the backbone of modules 04 and 05 — learn it first.

  prompt | model | parser
    |        |       |
    v        v       v
  fill    call    turn the reply into
  slots   Gemini  a clean string/object

4 · Why structure matters

A raw LLM returns a string. To use output in code you need structured data (a dict/object). Modules 03 (structured output) and 04 (parsers) are two routes to that — the single most important skill for turning an LLM into a reliable pipeline component.

5 · Pydantic & TypedDict (the schema tools)

You describe the shape you want with TypedDict (simple) or Pydantic BaseModel (with validation: types, ranges, defaults, descriptions). The model then fills that shape. You'll see both in module 03.

6 · Environment setup

pip install langchain langchain-google-genai langchain-community python-dotenv pydantic faiss-cpu pymupdf. Put GOOGLE_API_KEY in .env. Python 3.10+.

03 Module 03 — Structured Output

Make the model return typed data directly via model.with_structured_output(Schema) — four ways to declare the schema.

code

The four files

01  TypedDict                    # simplest schema
02  TypedDict + Annotated        # add per-field descriptions
03  Pydantic BaseModel           # validation: types, gt/lt ranges, defaults
04  JSON schema                  # a raw JSON schema
  • with_structured_output(Schema) makes the model return an object matching Schema — no manual parsing.
  • Pydantic (file 03) is the most powerful: Field(gt=1, lt=5, description=...) validates ranges and documents each field, and the description actively guides the model.
  • Use TypedDict for quick shapes, Pydantic when you want validation and clear field docs.
practice Run file 03 (Pydantic). Change a field's description and watch the extracted output change — the description is a prompt to the model, not just documentation.

04 Module 04 — Output Parsers

The other route to structure: let the model reply, then parse it. Parsers also plug into LCEL chains as the last step.

code

The parsers covered

StrOutputParser        # just get the string out of the reply (used in every chain)
JsonOutputParser       # parse the reply as JSON -> dict
StructuredOutputParser # define fields via ResponseSchema, parse them back
PydanticOutputParser   # parse into a validated Pydantic object

chain = prompt | model | parser   # parser is the last link
  • StrOutputParser is the one you'll use constantly — it unwraps the model's reply to a plain string so the next step gets clean text.
  • JsonOutputParser/PydanticOutputParser give structure without with_structured_output — useful when a model or provider doesn't support that.
  • The files include HF-endpoint and Gemini variants — same parser, different model.

Structured output (03) vs parsers (04) — which?

with_structured_output (03) is cleaner when your model supports it (Gemini/OpenAI do). Parsers (04) work with any model and compose naturally in LCEL chains. Know both; reach for structured output first, parsers when you need portability or a chain step.

practice Run 02_jsonoutputparser.py, then 04_pydanticoutputparser.py — same goal (structured result), two mechanisms. Note Pydantic also validates.

05 Module 05 — Chains (LCEL composition)

Compose steps with | into pipelines: sequential, parallel, and conditional.

code

sequential_chain.py — output feeds the next step

chain = prompt_temp1 | model | parser | prompt_temp2 | model | parser
result = chain.invoke({'topic': 'Unemployment in India'})
chain.get_graph().print_ascii()   # <- prints the pipeline as a diagram!
  • Generate a report → summarize it into 5 points, in one chain. The first step's output becomes the second's input.
  • chain.get_graph().print_ascii() is a gem — it draws your chain so you can SEE the flow. Use it on every chain.
code

The four chain shapes

simple_chain      : prompt | model | parser          (one straight line)
sequential_chain  : step1 -> step2 -> ...            (output feeds next)
parallel_chain    : run branches at once, merge      (RunnableParallel)
conditional_chain : branch based on a condition       (RunnableBranch)
  • Parallel: run several prompts on the same input simultaneously, then combine (e.g. generate notes AND a quiz from one text) — faster than sequential.
  • Conditional: route to different chains by a condition (e.g. sentiment → positive-reply vs negative-reply chain).
  • These three shapes cover most real pipelines. test_model.py/test_pydantic.py are small checks.
practice Run sequential_chain.py and read the print_ascii() output. Then run parallel_chain.py and compare the diagram — see how the shape changes.

07 Module 07 — Tools

A tool is a Python function the model can call. Tools give an LLM abilities it doesn't have on its own (search, math, file I/O, your APIs).

code

Defining a tool with @tool

from langchain_core.tools import tool
@tool
def analyze_data(text: str) -> dict:
    """Analyze text and return statistics."""   # <- the model READS this
    words = text.split()
    return {"word_count": len(words), "unique_words": len(set(words))}

# bind tools so the model can request them:
model_with_tools = model.bind_tools([analyze_data])
  • @tool turns a function into something the model can call. The docstring is critical — the model reads it to decide when to use the tool.
  • bind_tools([...]) tells the model which tools exist. The model then returns a tool call (name + arguments) which your code executes.
  • tool_calling.py and the notebooks show the full request→tool-call→result loop.
practice Run tool_calling.ipynb and watch the model choose a tool and return arguments. Change a tool's docstring to be vague and see the model stop using it — proof the docstring drives selection.

08 Module 08 — Agents

An agent gives the model tools AND the autonomy to decide which to call, in a loop, until the task is done. This is tools (07) + a reasoning loop.

code

08_Agents.py — a research agent with 3 tools

from langchain.agents import create_agent
@tool
def search_web(query: str) -> str: """Search the web..."""; ...
@tool
def analyze_data(text: str) -> dict: """Analyze text..."""; ...
@tool
def save_report(content: str) -> str: """Save the report..."""; ...

agent = create_agent(model=llm,
                     tools=[search_web, analyze_data, save_report],
                     system_prompt="You are a research assistant...")
result = agent.invoke({"messages": [{"role":"user",
                       "content":"Research AI safety trends and save a report"}]})
  • The agent is given three real tools and a goal. It decides: search the web → analyze results → save a report — choosing tools in sequence without you scripting the steps.
  • That autonomy is the difference from module 07: there YOU call the tool; here the AGENT decides when and which.
  • create_agent wires the model + tools + system prompt into the reasoning loop for you.
  • ⚠️ This file has the hardcoded key — fix per section 00 before running.

Tools vs Agents — the one-line distinction

Tools (07): the model can call functions, but you orchestrate. Agents (08): the model orchestrates itself — plans, calls tools, observes, repeats. Agents = tools + autonomy.

practice Run 08_Agents.py (after rotating the key + switching to env var). Read the printed result to see the agent's tool calls. Then add a 4th tool and a goal that needs it.

The through-line

You're learning to turn an LLM from a text-in/text-out box into a reliable component: give it structure (03/04), compose it into pipelines (05), ground it in documents (RAG), and give it abilities and autonomy (07/08). That's the full arc from prompt to agent.
